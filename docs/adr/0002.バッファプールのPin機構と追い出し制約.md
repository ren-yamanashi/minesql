# バッファプールの Pin 機構と追い出し制約

## Motivation

バッファプールから取得したバッファページを呼び出し側 (B+Tree の Iterator など) が長期間保持するパターンがあるが、現状の実装では以下の 2 つの問題がある

- 問題 1: Iterator 保持中のページが追い出されデータ破壊が起きる
  - Iterator は Search で取得したリーフページを保持し続ける
  - Iterator がリーフページを保持している間に、他のスレッドからの操作でバッファプールが満杯になり追い出しが発生すると、Iterator が保持しているバッファスロットが新しいページで上書きされる可能性がある
  - Iterator はバッファページ内のデータポインタを直接参照しているため、参照先のメモリが書き換わるとデータ破壊が起きる

- 問題 2: Iterator が Midpoint LRU の挙動と干渉する
  - 現状の Iterator は問題 1 を回避するため、Get / Advance のたびに `PageForRead` (バッファページを取得するメソッド) を呼び出して最新のバッファスロットを取得し直す設計になっている
  - `PageForRead` は内部で LRU の access 処理を呼ぶため、1 回の検索で同じリーフページに対して複数回 access が発生する (Search 時点で 1 回、Iterator.Get で 1 回など)
  - Midpoint LRU の「複数回アクセスされたページはホット」という判定が、本来「複数の独立した検索セッションを跨いだ再アクセス」を想定しているにもかかわらず、1 回の検索内の Iterator 内部の再アクセスで発火してしまう
  - 結果として、単発の検索で触れただけのリーフページが NewSublist に昇格してしまい、本来のホットページを押し出す
  - 現状はこの副作用を Iterator.Close で「Old Sublist の末尾に明示的に移動する」ことで打ち消しているが、LRU の意味そのものを歪めており、Iterator の利用側に「使い終わったら Close で追い出し優先化する」という非自明な責務を強いている

## Decisions

- バッファページに Pin (参照カウント) 機構を導入し、保持中のページを LRU の追い出し対象から除外する
- ダーティーページも追い出し対象から除外する
- 追い出し候補が見つからない場合は、ページクリーナーにフラッシュを依頼して dirty を解消させ、一定時間待機して再試行する
- Iterator など長期保持する利用側は内部で Pin / Unpin を管理し、外部利用者は Iterator の Close を呼ぶだけで Pin が解放されるようにする

## Context

### 案 1: Pin 機構を導入し、全 Pin 時はエラーを返却する

- バッファページに参照カウント (Pin) を持たせ、`PageForRead` 等で取得した時点で Pin を増やし、明示的に Unpin するまで追い出されないようにする
- `lru.evict` は Pin が 0 のページのみを追い出し候補とする
- 全ページが Pin されていて追い出し候補が見つからない場合はエラーを返却し、上位レイヤ (アクセスメソッド層やエグゼキュータなど) に判断を委ねる
- ダーティーページについては Pin とは別問題として扱い、現状通り追い出し時に同期的に書き出す

### 案 2: Pin に加えてダーティーページも追い出し不可とし、ページクリーナーでリカバリする

- 案 1 に加えて、ダーティーページも追い出し対象から除外する
  - 理由
    - Pin と組み合わせて「使用中のページの状態を勝手に変えない」というセマンティクスを統一するため
    - ページクリーナーとの連携で全 Pin 時のリカバリ経路を作るため
- 追い出し候補が見つからない場合、ページクリーナーにフラッシュ依頼のシグナルを送り、一定時間待機して再試行する
  - ページクリーナーがダーティーページをフラッシュすると dirty 制約が外れて追い出し可能なページが増える
  - Pin 自体は解放されないが、dirty 解消で追い出し候補の母集団が増えるため、Pin と dirty の同時保持で詰まっていた状態から回復できる

### 評価基準

- データ整合性: Iterator など保持中のページのデータ破壊が起きないか
- LRU 整合性: [LRU](../architecture/storage/buffer/lru.md) の Midpoint LRU の意図 (「複数の検索セッションを跨いで再アクセスされたページがホット」) と矛盾なく動作するか
- 全保護リソース時のリカバリ可能性: 全ページが追い出し対象外になった時に自動回復できるか
- 実装の複雑度と他コンポーネントへの影響範囲

### 評価結果

| 観点 | 案 2 (Pin + エラー) | 案 3 (Pin + dirty 不可 + cleaner) |
| --- | --- | ---|
| データ整合性 | 保証される | 保証される |
| LRU 整合性 | 保証される (Iterator は再取得不要) | 保証される (同左) |
| 全保護リソース時のリカバリ | エラーで上位に委譲、自動リカバリなし | ページクリーナー連携で自動リカバリ |
| 実装の複雑度 | 中 (Pin カウント管理、Iterator のリファクタ) | 高 (Pin + dirty 制約 + cleaner シグナル) |

### 結論

- 案 3 を採用する
- 案 2 でもデータ整合性と LRU 整合性は達成できるが、リカバリ経路を持たないため運用上は「最大ページ数 > 同時 Pin 数」の見積もりミスがクラッシュ要因になる
- 案 2 と比較すると実装の複雑度は上がるが、dirty 制約自体は追い出し時の条件分岐の追加にとどまり、ページクリーナーとの連携もシグナル用チャネル 1 本の追加で済むため、許容範囲と判断する
