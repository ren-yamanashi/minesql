## 概要

- Undo ログは、トランザクションのロールバックを実現するための仕組み
  - ACID のうち Atomicity を実現するための仕組み
- Undo ログには、トランザクションごとに複数の Undo ログレコードが記録される
- Undo ログレコードには、各操作に対してそれを取り消すために必要な情報が記録される
- ロールバックの際は、Undo ログに記録された Undo ログレコードを逆順に適用する

### Undo の系統

minesql の Undo ログは責務の異なる 2 系統に分かれ、それぞれ別の領域に書き出される

| 系統 | 用途 | 寿命 | 領域 |
| --- | --- | --- | --- |
| 通常 Undo | ユーザートランザクションの Rollback と MVCC の旧バージョン管理 | コミット後も他トランザクションの ReadView から参照される可能性がある間は保持 ([パージ](../access/purge.md) で回収) | 共有の Undo ログファイル |
| DDL Undo | [DDL](../access/ddl.md) の Rollback のみ | DDL の COMMIT 時にコンテナの中身 (= エントリ列) を即時物理破棄、 コンテナ自体は永続 (パージ経路を通らない) | DDL 専用領域コンテナ (カタログ初期化時に確保、 サーバライフタイム中永続) |

両者を分離するのは、MVCC への関与有無と寿命管理の違いがあるため。スキーマオブジェクトは旧バージョンとして読まれないため DDL Undo を ReadView 駆動で保持する必要がなく、専用領域に切り出すことで通常 Undo のパージ走査経路が DDL Undo の影響を受けない設計にできる

本ドキュメントの以降のセクションは通常 Undo のデータ構造と寿命を扱う。DDL Undo の取消種類や Rollback 論理は [DDL](../access/ddl.md) に集約する

### Undo ログレコードに記録される内容

Undo ログレコードには操作前の状態 (before image) を記録する。これには 2 つの目的がある。

- ロールバック: before image で B+Tree を上書きすれば操作前の状態に復元できる
- MVCC: 他のトランザクションが rollPtr を辿って Undo ログを参照すると、そのトランザクションの開始時点で可視だったバージョンのレコードが得られる

例として SoftDelete (論理削除) の場合、B+Tree 上のレコードは DeleteMark=0 → 1 に変わる。Undo ログには削除前のレコード (DeleteMark=0) を記録する。これにより:

- ロールバック時: Undo ログの DeleteMark=0 のレコードで上書きし、削除をなかったことにできる
- MVCC 時: 他のトランザクションが rollPtr を辿ると DeleteMark=0 のレコードが見え、そのトランザクションにとっては行が存在する状態として読める

| 操作 | レコードに記録される内容 |
| --- | --- |
| Insert | 挿入したレコードの内容 |
| Delete | 削除前のレコードの内容 (DeleteMark=0) |
| Update (PK 不変) | 更新前のレコードの内容と更新後のレコードの内容 |
| Update (PK 変更) | Insert と Delete の 2 操作で記録されるレコードの内容 |

#### Update に更新後のレコードも記録する理由

- ロールバックには更新前のレコードがあれば十分だが、Update には更新後のレコードも記録する
- これは [Purge](../access/purge.md) で、論理削除済みのセカンダリインデックスエントリを物理削除する際に「どのセカンダリキーを物理削除すべきか」を Undo レコードから復元するために必要となる

#### Delete Undo の DeleteMark=0 が意味するもの

- Delete (SoftDelete) の Undo レコードには「削除前のレコード = DeleteMark=0 の状態の行」が記録される
- これにより以下が成立する
  - ロールバック時: Undo レコードで上書きすれば DeleteMark=0 の状態に戻り、削除をなかったことにできる
  - MVCC 時: 他のトランザクションが `rollPtr` を辿るとこの行が見え、「行が存在する状態」として読める
- つまり Undo レコードに保持される行は常に「操作前の active 状態」を表現し、MVCC で旧バージョンとして見える行は常に DeleteMark=0 として再構築される

### Undo ログレコードの寿命

- 操作種別ごとに Undo ログレコードの寿命が異なる

| 種別 | コミット後の扱い |
| --- | --- |
| Insert | コミット時に History List (= パージ走査の駆動源となるメモリ上の管理リスト) から取り除く (他のトランザクションが未コミットの挿入を参照することはなく、コミット後は挿入された行自身が最初の可視バージョンになるため、旧バージョンとして遡る必要がない) |
| Update / Delete | [Purge](../access/purge.md) で破棄する (他のトランザクションが Undo チェーンを辿って旧バージョンを参照する可能性があるため、即座には破棄できない) |

- Insert の Undo は、History List から外されるとパージ走査の対象から外れる。ただし、Undo ページ上のレコード実体は MVCC チェーンの終端判定 (Undo を辿って `rollPtr` が無効値に到達したら「これ以上遡れない」と判定する) で参照される可能性があるため、コミット後の即座に物理領域を解放するわけではなく、Undo ページの再利用契機 (= 後続トランザクションが Undo を書き込んで上書きするとき) に物理領域が解放される
- Update / Delete の Undo は、現存するどの Read View からも参照されなくなった時点で破棄可能と判定される (詳細: [パージ](../access/purge.md))
- 上表の通常 Undo に対し、DDL Undo は ReadView から参照される経路がないため、DDL の COMMIT 時にコンテナの中身 (= エントリ列) が即時物理破棄される (コンテナ自体は永続。 パージ走査の対象外。 詳細: [DDL の完了処理](../access/ddl.md#ddl-の完了処理))

### 完了済み未パージ trx 集合の再構築

[パージ](../access/purge.md) は「コミット済みで、 ReadView からも参照されなくなった Undo」 を駆動源とする。 そのために必要なのは「コミット済みかつ未パージのトランザクション ID 集合」 で、 これは Undo ページの走査結果から再構築できる

- INSERT の Undo はコミット時に History List から外され、 パージ対象にならない。 INSERT の Undo がページ上にレコード実体として残っていても、 パージ走査の駆動源としては扱わない
- UPDATE / DELETE の Undo はパージで破棄されるまで Undo ページ上に残る。 残っている UPDATE / DELETE の Undo を持つトランザクション ID は、 必ず「コミット済みかつ未パージ」 (= パージの駆動対象) になる
  - 未コミットのトランザクションは Rollback で Undo が全破棄されるか、 Commit を経て上記の寿命に従う。 アクティブ状態のままページ上に残るのは、 そのトランザクションがまだ完了していない場合のみで、 アクティブな ID はメモリ上のアクティブトランザクション一覧で別管理されている

起動時に Undo ページを先頭から末尾まで走査し、 UPDATE / DELETE 種別の Undo レコードに含まれるトランザクション ID を集めれば、 再起動を挟んだ後でも「コミット済みかつ未パージ」 のトランザクション ID 集合が復元できる。 これにより、 Redo ログのチェックポイント切り詰めや[リカバリ完了処理](../access/crash-recovery.md#4-リカバリ完了処理) の Redo クリアによって完了情報が失われた状態でも、 パージはディスクに残った Undo を正しい駆動源として再開できる

### Undo 書き込みの mini-transaction 境界

Undo ページへの書き込みは、 対応するデータ操作の mini-transaction (= B+Tree 上のレコード変更を伴うもの) とは別の独立した mini-transaction で完結させる。 データ操作側の mini-transaction は、 Undo 側の mini-transaction が完了した後に開始し、 確定した Undo ポインタを参照する

- 独立した mini-transaction とすることで、 Undo ページの変更を記録した Redo レコードが、 対応するデータ操作の Redo レコードよりも必ず先にログバッファへ追記される
  - 未コミットの変更がデータページとしてディスクに反映された場合でも、 対応する Undo ページの Redo は必ずディスクに先行して存在する。 これにより、 クラッシュリカバリ時に Undo ページを復元して未コミットトランザクションをロールバックできる (詳細: [Redo ログ - データ変更時の書き込みフロー](./redo.md#データ変更時))
- 独立した mini-transaction とすることで、 Undo ページの Pin とラッチも Undo 書き込みの完了時に解放され、 データ操作の mini-transaction の境界に持ち越されない
  - Undo ページは複数の同時並行トランザクションが書き込みを共有する性質を持つため、 一方のトランザクションが Undo ページの所有を長時間握り続けると後続の Undo 書き込みが阻害される。 Undo を独立した mini-transaction として閉じることで、 Undo ページの所有期間を 1 件の Undo レコード書き込みの間だけに限定できる

## データ構造

- Undo ログは、Undo ページに記録される
- Undo ページは `undo.db` ファイルに永続化される
- キャッシュにはデータページと同じバッファプールを使用

### Undo ログページ

- Undo レコードを格納するためのページ
- B+Tree ではなく単純な単方向リンクリスト (ページが満杯になると新しいページが割り当てられる)

| 領域 | バイト数 | 説明 |
| --- | --- | --- |
| ヘッダー | 2 | ボディ部分の使用済みバイト数 |
| ヘッダー | 4 | 次の Undo ページの PageNumber |
| ボディ | 可変 | Undo レコードが先頭に順から詰められる |

```txt
| ヘッダー | レコード#0 | レコード#1 | レコード#2 | 空き ... |
          ↑ Undo ポインタのオフセットは各レコードの先頭を指す
```

- 追記専用なので、B+Tree ノードのような [Slotted Page](../btree/slotted-page.md) の仕組み (ポインタ配列による間接参照) は持たず、レコードを隙間なく順に詰めるだけ
- そのため「ページ番号 + バイトオフセット」だけでレコードの先頭を一意に指せる (詳細: [Undo ポインタ](#undo-ポインタ))

※ Undo ログページへの書き込みは [Redo ログに記録され](./redo.md#書き込みフロー)、Undo ログページの即時フラッシュは行わず、永続性は Redo ログによって担保される

#### Undo ページ切替時の Redo ログ順序

現在のページが満杯になり新ページを割り当てるとき、Redo ログには以下の順序で記録する

1. 新ページの実体 (初期化 + 追加対象レコード) を Redo に書く
2. 旧ページの「次ページへのリンク (= 新ページの PageNumber)」更新を Redo に書く

順序を逆 (リンク更新を先) にすると、中途失敗・クラッシュで Redo にリンク変更だけが残ったままリカバリが適用され、旧ページが「Redo に実体のないページ」を指す状態になり、Undo チェーン走査が壊れる

「新ページの実体を先」とすることで、中途失敗時の最悪ケースは「初期化された新ページが Redo に残り、誰もそれを指していない (dangling page)」となり、整合性を壊さない

### Undo ログレコード

| offset | バイト数 | 項目 | 説明 |
| --- | --- | --- | --- |
| 0 | 4 | トランザクション ID | このレコードを記録したトランザクションの ID |
| 4 | 4 | Undo 番号 | トランザクション内の連番 |
| 8 | 1 | レコード種別 | 操作の種別 (1=Insert, 2=Delete, 3=Update) |
| 9 | 2 | データ長 | 変更内容のバイト数 |
| 11 | 可変 | 変更内容 | レコード種別に応じたデータ |

変更内容の先頭には、この操作で上書きされる前のレコードが持っていた `lastTrxId` と `rollPtr` が記録される\
これにより、Undo ログを辿って旧バージョンを参照できる (詳細: [トランザクション - 可視性の判定](../access/mvcc.md#可視性の判定))

#### 変更内容

| offset | サイズ | 項目 | 説明 |
| --- | --- | --- | --- |
| 0 | 4 バイト | prevLastTrxId | 上書き前の行の `lastTrxId` |
| 4 | 6 バイト | prevRollPtr | 上書き前の行の `rollPtr` |
| 10 | 4 バイト | FileId | テーブルの FileId |
| 14 | 可変 | カラムセット | カラムセット (下記参照) |

#### カラムセット

カラムセットは、行を表す B+Tree のレコード 1 件を格納する単位\
カラムセットは操作種別に応じて 1 つまたは 2 つ格納される

- Insert / Delete: 1 セット (操作対象の行)
- Update (PK 不変): 2 セット (更新前の行、更新後の行)

セット内の要素はテーブルのカラム値ではなく、B+Tree のレコードを構成する 3 つの領域 (ヘッダー領域・キー領域・非キー領域) のバイト列であり、この順に格納される (領域の詳細: [ノード - レコード](../btree/node.md#レコード))

各カラムセットの形式

| サイズ | 項目 | 説明 |
| --- | --- | --- |
| 2 バイト | 要素数 | セット内の要素の数 (常に 3) |
| 可変 | 要素データ | 以下の形式を要素数だけ繰り返す |

各要素データの形式

| サイズ | 項目 | 説明 |
| --- | --- | --- |
| 2 バイト | データ長 | データのバイト数 |
| 可変 | データ | 領域のバイト列 |

##### 例: カラムセットのバイト列

`id` をプライマリキーとするテーブルの行 `(id=1, name=Alice)` を格納するカラムセット 1 つ分のバイト列は以下のようになる

```txt
00 03                          要素数 = 3

00 01                          要素 1 (ヘッダー領域) のデータ長 = 1
00                             deleteMark = 0

00 09                          要素 2 (キー領域) のデータ長 = 9
31 00 00 00 00 00 00 00 01     プライマリキー "1" の Memcomparable エンコード

00 13                          要素 3 (非キー領域) のデータ長 = 19
00 00 00 01                    lastTrxId
00 00 00 00 00 00              rollPtr
41 6C 69 63 65 00 00 00 05     非キーカラム "Alice" の Memcomparable エンコード
```

- カラムセットと要素は論理的には入れ子だが、ポインタによる間接参照はなく、全体が 1 本の連続したバイト列として格納される (境界はすべて長さ情報から復元できる)
- Update の場合は、この塊が 2 つ (更新前の行 → 更新後の行) 連続して並ぶ

#### Undo ポインタ

- Undo ログレコードへのポインタは「Undo ページのページ番号」と「ページ内のオフセット」の 2 つで一意に特定される (合計 6 バイト)
- プライマリインデックスのレコードが持つ `rollPtr` は、その行に対する直前の操作の Undo レコードを指す Undo ポインタ
- Undo レコード内の `prevRollPtr` は、さらに 1 つ前のバージョンの Undo レコードを指す Undo ポインタ
- Undo ポインタには「前バージョンが存在しないこと」を示す番兵値 (無効値) が予約されている
  - Insert の Undo レコードの `prevRollPtr` がこれに該当し、Undo チェーンの終端マーカーとなる
- Undo ポインタから Undo レコードを取得する流れ
  1. Undo ポインタの「ページ番号」から該当の Undo ページをバッファプール経由で取得する
  2. ページ内のオフセットから Undo レコードのバイト列を直接デコードする
     - Undo ページは追記専用で、レコードは順に詰めて格納されているため、オフセットがレコードの先頭を指す

#### Undo レコードから旧バージョンの行を再構築する論理

- 可視性判定で不可視と判定された場合、Undo レコードから旧バージョンを再構築する必要がある
  - 詳細: [MVCC - Undo チェーン遡及](../access/mvcc.md#undo-チェーン遡及)
- 各 Undo レコード種別から取り出せる情報は以下のとおり

| Undo レコード種別 | カラムセット数 | 旧バージョンとして使うカラムセット | 旧バージョンの DeleteMark |
| --- | --- | --- | --- |
| Insert | 1 セット (挿入された行) | (旧バージョンは存在しない。チェーン終端) | - |
| Update | 2 セット (更新前 / 更新後) | 1 セット目 (更新前の行) | 0 (更新前は active なレコード) |
| Delete | 1 セット (削除前の行) | そのカラムセット | 0 (削除前は active なレコード) |

- 旧バージョンの `lastTrxId` と `rollPtr` は、Undo レコードの「変更内容」の先頭 (`prevLastTrxId` / `prevRollPtr`) から取得する
  - これにより、可視性判定をさらに 1 段階遡って実施できる
