## 概要

- [クラッシュリカバリ](../access/crash-recovery.md)時などに、バッファプールには反映されているがディスクには未反映の変更内容などを適用するための仕組み
  - ACID のうち Durability を実現するための仕組み
- Redo ログは、トランザクションの変更内容を記録する追記専用のシーケンシャルログ
- ダーティーページがディスクへフラッシュされる前に、対応する Redo ログを必ずディスクへ書き出す (Write-Ahead Logging)
  - WAL 原則はディスクへの永続化順序の制約であり、メモリ上の操作順序とは独立。バッファ上のページ変更を先に行ってから対応する Redo レコードをログバッファへ追記してもよい (詳細は[書き込みフロー](#書き込みフロー))
  - 詳細: [Durability を実現するためのアルゴリズム](../../../about/durability.md)

## データ構造

### Redo ログファイル

- Redo ログは単一のファイル (`redo.log`) に永続化される
- ファイルはファイルヘッダーとログレコードの連続で構成される

```txt
|  ファイルヘッダー  | レコード | レコード | レコード | ... |
0                 16
```

### ファイルヘッダー

| offset | バイト数 | 項目 | 説明 |
| --- | --- | --- | --- |
| 0 | 4 | Flushed LSN | ディスクにフラッシュ済みの最大 LSN |
| 4 | 4 | Checkpoint LSN | この LSN 以前の Redo レコードは不要であることを示す |
| 8 | 8 | 予約領域 | 将来の拡張用 |

- Flushed LSN はディスクにフラッシュ済みの最大 LSN を保持するとともに、再起動時に LSN 採番を再開する起点としても利用される (次に採番する LSN は Flushed LSN + 1)
- Redo ログの切り詰めにより末尾レコードが取り除かれた場合でも、過去に採番済みの LSN を再利用しないよう、Flushed LSN は「残されたレコードの最大 LSN」と「切り詰め基準 LSN」のうち大きいほうを採用する

### Redo ログレコード

- 各レコードは可変長で、先頭から順に隙間なく詰めて記録する
- レコードの種別は以下の 5 つ:
  1. ページ変更
     - データページや Undo ページへの変更を示す
     - 変更内容としてページ全体のコピー (4096 バイト) を持つ
  2. COMMIT
     - トランザクションのコミットを示す
     - 変更内容は持たない
  3. ROLLBACK
     - トランザクションのロールバックを示す
     - 変更内容は持たない
  4. mini-transaction 開始
     - 1 つの mini-transaction の開始を示す境界マーカー
     - 変更内容は持たない
  5. mini-transaction 終了
     - 1 つの mini-transaction の終了を示す境界マーカー (開始マーカーと対になる)
     - 変更内容は持たない
- ページ変更レコードの「変更内容」には、差分ではなくページ全体のコピーを記録する。リカバリ時はページをそのまま上書きする
  - 設計背景: [ADR: Redo ログのページ変更記録方式](../../../adr/0001.Redoログのページ変更記録方式.md)

| offset | バイト数 | 項目 | 説明 |
| 0 | 4 | [LSN](../../../about/durability.md#log-sequence-number-lsn) | このレコードの LSN |
| 4 | 4 | TrxId | 変更を行ったトランザクション ID |
| 8 | 1 | レコード種別 | 操作種別 (ページ変更, COMMIT, ROLLBACK, mini-transaction 開始, mini-transaction 終了) |
| 9 | 8 | PageId | 変更対象ページの PageId |
| 17 | 2 | データ長 | 変更内容のバイト数 |
| 19 | 可変 | 変更内容 | レコード種別に応じたデータ |

- データ長フィールドは 2 バイト (符号なし整数) であるため、1 レコードの変更内容は最大 65,535 バイトに制限される
- 現在のページサイズは 4,096 バイトなのでページ変更レコードでも十分なマージンがあるが、将来ページサイズを大きくする場合はこの上限を超えないことが制約として効いてくる

## Page LSN

- 各[ページ](../page/page.md)は先頭 4 バイトのページヘッダーを Page LSN として使用する
- Page LSN はそのページに最後に適用された Redo ログレコードの LSN を記録する
- クラッシュリカバリ時、Redo ログレコードの LSN がページの Page LSN 以下であれば、そのレコードは適用済みなのでスキップする

## mini-transaction の区切り

- 1 つの操作 ([mini-transaction](../buffer/latch.md#mini-transaction)) が複数ページを変更することがある (例えば B+Tree の[ノード分割](../btree/btree-insert.md)は親ノードと分割前後のリーフノードを変更する)
- その複数のページ変更レコードを 1 つのまとまりとして識別できるよう、Redo ログには mini-transaction の開始マーカーと終了マーカーを記録する
- 開始マーカーと終了マーカーの間に位置するページ変更レコード群が、1 つの mini-transaction に属するページ変更となる
- クラッシュリカバリ時には、開始マーカーに対応する終了マーカーが存在する mini-transaction のみを適用し、終了マーカーを欠く mini-transaction (= 書き出し途中でクラッシュした mini-transaction) は破棄する
- 開始マーカーと終了マーカーで囲まれていないページ変更レコードはクラッシュリカバリ時に適用されない (=Redo ログにページ変更を記録する全ての操作は、mini-transaction 境界マーカーで囲む必要がある)
- mini-transaction の境界内で変更したページの Pin とラッチは、 終わりの区切りに到達するまで解放しない。 Pin が解放されていないページはバッファプール側で[フラッシュ対象から除外される](../buffer/buffer-pool.md#ページのフラッシュ) ため、 終わりの区切りを欠く mini-transaction が変更したダーティーページがディスクへ書き出されることはない。 リカバリ側は終わりの区切りを欠く mini-transaction を破棄するだけで整合性が保たれる

## 書き込みフロー

データ変更時とコミット時で、Redo ログの書き込みタイミングが異なる

### データ変更時

1 つの論理操作 (挿入・更新・削除) は、 Undo 書き込みの mini-transaction とデータページ変更の mini-transaction を順に実行することで完結する。 Redo ログ上では、 それぞれの mini-transaction が独立した[開始マーカー](#mini-transaction-の区切り) と終了マーカーで囲まれる

1. Undo 書き込みの mini-transaction を開始する
2. バッファプール上の Undo ログページに Undo ログレコードを書き込む
3. Undo ログページへの変更を Redo ログに記録する
4. Undo 書き込みの mini-transaction を終了し、 Undo ポインタを確定する
5. データページ変更の mini-transaction を開始する
6. バッファプール上のデータページを変更する (= 4 で確定した Undo ポインタをレコードに埋める)
7. データページへの変更を Redo ログに記録する
8. データページ変更の mini-transaction を終了する

- Redo ログにはページ全体のコピーを記録する ([ADR: Redo ログのページ変更記録方式](../../../adr/0001.Redoログのページ変更記録方式.md)) ため、バッファ上のページ変更後に Redo ログへ記録する
- WAL 原則 (ダーティーページのフラッシュ前に対応する Redo ログを永続化) はディスクへのフラッシュ順序で担保されており、メモリ上の操作順序とは独立
  - メモリ上のバッファはサイズ上限到達時にコミットを待たずフラッシュされるが、対応するダーティーページのフラッシュは常にその後で行われるため WAL 原則は崩れない
- Undo 書き込みの mini-transaction を先に終了させることで、 Undo の Redo がログバッファ上で必ずデータの Redo より先に位置する。 これにより、 未コミットの変更がデータページとしてディスクに書かれた場合でも、 対応する Undo ログページの Redo は必ずディスクに存在するため、 クラッシュリカバリ時に Undo ログページを復元して未コミットトランザクションをロールバックできる (詳細: [Undo ログ - Undo 書き込みの mini-transaction 境界](./undo.md#undo-書き込みの-mini-transaction-境界))

### コミット時

1. Redo ログをディスクにフラッシュする

※(データページの) バッファプールのダーティーページのディスクフラッシュは、コミットとは無関係のバッファプールの都合 (LRU やチェックポイント) で行われる\
ただし、ダーティーページをディスクにフラッシュする前に、そのページに関連する Redo ログが先にディスクに書かれている必要がある

## 永続化のタイミング

永続化のタイミングは以下の 2 つ

- トランザクションのコミット
- チェックポイントによりデータページがディスクにフラッシュされる前

これにより、クラッシュリカバリ時にデータページが正しく復元できる

- コミット済みの変更 (=データページの変更) がディスクに反映されてない場合
  - クラッシュリカバリ時に Redo ログを使用して変更を適用する
- 未コミットの変更 (=データページの変更) がディスクに反映されている場合
  - WAL 原則により、必ず Redo ログもディスクに反映されているため、Redo ログから Undo ログを復元でき、復元した Undo ログを使用して未コミットのトランザクションをロールバックできる ([データ変更時の書き込みフロー](#書き込みフロー)に記載のとおり)

## DDL 経路と起動時初期化の扱い

データ操作 (DML) だけでなく、データ定義操作 (DDL: CREATE TABLE 等) と起動時の永続オブジェクト初期化 (カタログヘッダー / B+Tree メタページ / Undo ページ等) もすべて Redo に記録する

- DDL もページ変更を伴うため、記録しないとクラッシュ後にメタテーブルやカタログヘッダーの変更が復元されない
- 起動時初期化は idempotent (= 既に初期化済みの場合は再実行しても安全) なので、未コミットでロールバックされても再実行で復元可能

DDL や起動時初期化を行うために、ユーザートランザクションとは別にシステム予約のトランザクション ID を採用する

- システム予約のトランザクション ID はユーザー採番と衝突しない値を 1 つ確保する
- DDL や起動時初期化の mini-transaction はこのトランザクション ID で記録する
- リカバリでは通常のトランザクション ID と同じ扱いとする (未完了であればロールバック対象に含める)

## パージのバックグラウンド削除と Redo 記録

[パージ](../access/purge.md)は MVCC で不要になった論理削除済みレコードをバックグラウンドで物理削除する処理だが、その物理削除もページ変更を伴うため Redo に記録する

- 記録しないと、クラッシュ後のリカバリで「物理削除されたはずの古バージョン」がディスクから復活し、その後の挿入や検索と矛盾する状態になる
- パージは通常運用時にのみ実行され、リカバリ中には実行されない (リカバリ完了後にバックグラウンドゴルーチンが再開される) ため、リカバリ中に重複記録される心配はない

パージは内部的にユーザートランザクションを伴わないバックグラウンド処理であり、専用の予約トランザクション ID を用意してその ID で mini-transaction を記録する

- パージ専用の予約トランザクション ID は、ユーザー採番および DDL / 起動時初期化用のシステム予約 ID のいずれとも衝突しない値を 1 つ確保する
- パージは常に同期的に完結する (途中で別の操作と境界を共有しない) ため、リカバリではパージ専用 ID のトランザクションを未完了とみなしてもデータ整合性に影響しない

## ロールバックの Redo 記録

[ロールバック](../access/transaction.md#rollback-ロールバック)は通常運用時とリカバリ中で Redo への扱いを変える

- 通常運用時のロールバック: ロールバック対象のトランザクション ID をそのまま使い、Undo の逆適用によるページ変更を Redo に記録する。ロールバック完了時に Redo 上のロールバックマーカーで境界を閉じる。これによりロールバック完了直後にクラッシュしてもロールバック後の状態が復元される
- リカバリ中のロールバック: 未完了トランザクションに対する Undo 逆適用はリカバリ自身の処理として実行され、Redo には何も記録しない。リカバリは終了時にチェックポイント相当の操作で過去の Redo を切り詰めるため、リカバリ中の変更を二重に Redo へ記録する意味がなく、また idempotent な再実行を阻害しないために記録を避ける

通常運用時とリカバリ中で同じ Undo 逆適用ロジックを共有しつつ、上記の差は呼び出し側で mini-transaction の作り方を切り替えることで実現する (記録ありの書き込み mini-transaction か、記録なしの読み取り mini-transaction か)

## チェックポイントによる切り詰め

- チェックポイント時には、不要になった過去の Redo レコードを切り詰めて Redo ログファイルを圧縮する
- 既存の Redo ログファイルを直接書き換えるのではなく、一時ファイルに「更新後のファイルヘッダー」と「残すべきレコード列」を順に書き出し、書き終わった一時ファイルを原子的にリネームして本ファイルに置き換える
  - 切り詰めの途中でクラッシュしても、本ファイルは旧状態のまま残るため Redo ログは破損しない
  - リネームはファイルシステム側で原子的に行われるため、本ファイルが「旧状態」か「新状態」のいずれかに必ず収まる
- 起動時には残骸の一時ファイルがあれば削除してから Redo ログを開く
  - 前回のリネーム前にクラッシュすると一時ファイルが残ったまま起動することがあるため、リカバリ前にその残骸を取り除いてファイル状態を一意にする

## クラッシュ時の末尾レコードの扱い

Redo ログレコードの追記中にクラッシュすると、ファイル末尾には書きかけの不完全なバイト列が残ることがある。リカバリ時の扱いは、不完全な部位がレコードヘッダーに到達しているかどうかで異なる

- レコードヘッダー (固定長部分) に満たない端数バイトが末尾に残っている場合: 「書きかけのレコード」として無視する。次にレコードを追記したときにそのまま上書きされるため、データ整合性には影響しない
- レコードヘッダーまでは存在するが、そのヘッダーが示すデータ長に対して可変長部分が途中で切れていたり内容が壊れている場合: 破損として扱い、リカバリはエラーで停止する。書き出し境界はレコードヘッダーがディスクへ到達した時点と読み出せる時点の両方で揃っているはずなので、ここに不整合がある状態は許容しない
