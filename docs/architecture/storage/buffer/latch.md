# ラッチ

## 概要

- ラッチ (Latch) は、ページなどのデータ構造に対する物理的な排他制御
- [ロック](../lock/lock.md)との違いは保持期間と保護対象にある
  - ロックは論理的な排他制御で、トランザクションの期間中保持され、対象はレコードなどの論理的なデータ
  - ラッチは物理的な排他制御で、1 つの原子的なページ操作の間だけ保持され、対象はページなどのデータ構造そのもの
- ラッチが必要な理由は、[Pin](./buffer-pool.md) もロックもページ内容の同時アクセスを防がないため
  - Pin はページが追い出されないことを保証するだけで、内容の同時書き換えは防がない
  - ロックはレコード単位の論理的な競合を防ぐだけで、同じページ上の別レコードを触る操作同士や、読み取りと書き込みが同じページの内容に同時アクセスすることは防がない
  - 保護がないと、書き換え途中のページを読んだり、ディスクへ書き出したりして内容が壊れる

## ラッチが守る競合

ラッチは、同じページの内容に対する以下の同時アクセスを直列化する

- 書き込みとフラッシュ
  - フラッシュ処理が書き換え途中のページをディスクへ書き出すのを防ぐ
- 書き込みと書き込み
  - 同じページ上の別レコードを更新する操作同士が、ページ内容を同時に書き換えるのを防ぐ
- 読み取りと書き込み
  - 読み取り中のページが書き換えられ、途中状態を読むのを防ぐ
    - MVCC の一貫性読み取りはレコードのバージョンの可視性を判定する仕組みであり、ページ内容の途中状態を読むことは防げないため、物理的な読み取りの間はラッチで保護する

## ラッチのモード

| モード | 用途 |
| --- | --- |
| Shared (S) | 読み取り。複数の操作が同時に保持できる |
| Exclusive (X) | 書き込み。1 つの操作のみが保持できる |
| Shared-Exclusive (SX) | 後で Exclusive へ昇格しうる読み取り。他の Shared とは同時に保持できるが、他の SX や Exclusive とは競合する |

### ラッチの競合

| 保持中 \ 要求 | S を要求 | SX を要求 | X を要求 |
| --- | --- | --- | --- |
| 保持者なし | 競合しない | 競合しない | 競合しない |
| S を保持 | 競合しない | 競合しない | 競合する (待機) |
| SX を保持 | 競合しない | 競合する (待機) | 競合する (待機) |
| X を保持 | 競合する (待機) | 競合する (待機) | 競合する (待機) |

### 待機キューと公平性

- 取得が競合する要求は、ラッチごとの待機キューに到着順 (FIFO) で並ぶ
- 待機キューの先頭に立った要求から順に付与され、後から到着した互換要求 (例: 既に Shared 取得者がいるところに後続の Shared が来るケース) であっても、先頭が Exclusive 待機者なら追い越して付与されない
- これにより、長く待たされる Exclusive 要求が後続の Shared 要求の連続到着で永続的に弾かれる「飢餓 (starvation)」を防いでいる

## Pin とラッチのライフタイムの違い

Pin とラッチは保護する対象が異なるため、保持する期間も異なる

- Pin (追い出し防止) は、操作の範囲を超えて保持してよい
  - 例えば順次走査 (スキャン) は、参照中のページが追い出されないように、走査が続いている間ずっと Pin を保持する
- ラッチ (内容保護) は、内容の一貫性が必要な最小の区間だけ保持する
  - 例えば順次走査は、1 レコードを読み出す瞬間だけ短期の S ラッチを取り、読み出し後はすぐ解放する。これにより、走査が長く続いても、その間に他の書き込みが同じページを更新できる

## mini-transaction

- 1 つの原子的なページ操作 (1 回の検索・挿入・削除など) の間に獲得した Pin とラッチを 1 つの単位にまとめ、操作の完了時にまとめて解放する。この操作スコープを mini-transaction と呼ぶ
  - トランザクション (論理的・利用者単位・コミットまで長期に保持) とは別物で、1 つの論理トランザクションは多数の mini-transaction から成る
  - 1 つの SQL ステートメント (e.g. 1 回の SELECT) も、内部では複数の mini-transaction から構成される
    - 例えば最初の B+Tree 降下は 1 つの mini-transaction、走査中の各レコード取得 (旧バージョンの再構築を含む) はそれぞれ別の mini-transaction として扱う
- Pin もこの単位に含めるのは、追い出し防止の Pin の解放を、その Pin を獲得した操作の境界に一致させるため
  - Pin はページを取得するたびに増えるが、解放点が操作のあちこちに散らばると、解放漏れで追い出し不能なページが蓄積したり、解放する位置を取り違えたりしやすい
  - 解放を「操作の完了」という 1 点に集約することで、Pin の所有が操作単位で追えるようになる。ラッチも同じ操作スコープで解放されるため、同じ単位にまとめて扱う
- 例外として、順次走査へ引き渡すページの Pin だけはこの単位から切り離して走査側へ移譲する
  - 順次走査は、最初の検索操作 (mini-transaction) が終わった後も、レコードを読み進める間そのリーフページを参照し続ける。操作の完了時に Pin を解放するとそのページが追い出されうるため、Pin だけを走査側へ引き渡し、走査が当該ページを参照し終えた時点で解放する

### 同一 mini-transaction 内での同じページの再取得

1 つの mini-transaction の中で同じページを 2 度以上要求する場合、ラッチの所有モードは以下の規則で整える

- 既に保持しているのと同じか弱いモードの再要求は、二重取得せずに既存の所有モードをそのまま尊重する
  - 例: 既に Shared を保持しているページに対する Shared 再要求や、既に Exclusive を保持しているページに対する Shared / Exclusive 再要求は、新たにラッチを取り直さない
- 既に Shared を保持しているページに対して Exclusive を要求した場合は、いったん Shared を解放してから Exclusive を取り直す
  - これは原子的な upgrade ではなく、Shared 解放と Exclusive 取得の間に他の操作が同じページの Exclusive を取得する可能性がある
  - そのため、Exclusive 取得後に呼び出し側はページ内容を再検証し、再取得前に観測した状態に依拠しないこと

## フラッシュとの協調

- フラッシュを行う側は、ダーティーページをディスクへ書き出す前に、そのページの S ラッチを取得する
- フラッシュには 2 つの経路があり、S ラッチの取り方が異なる
  - ページクリーナーによる定期フラッシュ: S ラッチを取得する。書き込み中の操作が X ラッチを保持している間は、その解放を待つ
  - 追い出し圧の救済フラッシュ: 追い出し候補を確保できない操作自身が実行するフラッシュ。S ラッチの取得を試み、取得できないページはスキップする
    - 解放を待ってしまうと、その操作自身が保持している X ラッチと「追い出し可能ページの供給」との間で循環待ちが成立するため、待たずにスキップする
- どちらの経路でも書き出しは S ラッチの保持中に行われるため、書き換え途中のページがディスクへ書き出されることはない
