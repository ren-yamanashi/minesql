# B+Tree の並行制御

## 概要

- 複数のトランザクションが同じ B+Tree を同時に読み書きするとき、ページ内容と B+Tree 構造の物理的な一貫性を保つために[ラッチ](../buffer/latch.md)を使う
- B+Tree では 2 種類のラッチを使う
  - ページラッチ
    - 個々のページ内容を守る
    - 読み取りで Shared、書き込みで Exclusive を取る
  - B+Tree レベルのラッチ
    - B+Tree 全体に対して 1 つ取るラッチ
    - B+Tree 構造そのもの (どのページがどの親子・兄弟関係にあるか) の変更と探索が競合しないように制御する

## B+Tree レベルのラッチ

- 個々のページラッチがページ内容を守るのに対し、B+Tree レベルのラッチは構造そのものの変更と探索が競合しないように制御する
- 通常の探索や 1 つのリーフノードに収まる更新は B+Tree 構造を変えないため、B+Tree レベルの Shared で足りる
- 一方で、[分割](./btree-insert.md)や[マージ](./btree-delete.md)が発生するケースでは、B+Tree レベルの SX を取る
  - これにより、構造変更中も探索や構造を変えない更新を並行して通せる

## ラッチの取得順序

- ラッチは常に一定の順序で取得することで、ラッチ同士のデッドロックを避ける
  - B+Tree は上 (ルート) から下 (リーフ) へ取得する
  - リーフの連結リストは左から右へ取得する

## 探索

- ルートからリーフへ降りる間、親のラッチを子へ持ち替えながら進む
  1. ルートに Shared ラッチを取る
  2. 現在のノードから、次に降りる子の位置を読む
  3. 子に Shared ラッチを取ってから、親の Shared ラッチを解放する
  4. リーフに達するまで 2〜3 を繰り返す
  - 先に親を解放すると、その隙に別の操作が B+Tree 構造を変え、辿るべき子が変わってしまう可能性があるため、子のラッチをとってから親を解放する

- 目的のレコードを含まないリーフを経由する場合 (検索キーがリーフの末尾を超えて隣のリーフへ進むときなど) も、経由するリーフに S ラッチを取る
  - 隣のリーフへ移るときは、移り先の S ラッチを取ってから手元のリーフのラッチを解放する

## 更新 (楽観・悲観)

更新の多くは 1 つのリーフノードに収まり B+Tree 構造を変えない。一方で分割やマージは複数ページと構造を変える。前者を楽観、後者を悲観として 2 段構えで扱う

- 楽観
  - B+Tree レベルの Shared を取り、ルートから目的のリーフへ降りる。途中のブランチノードは探索と同じく Shared で持ち替え、目的のリーフだけ Exclusive を取る (更新は目的のリーフが一意に定まるため、探索のように隣のリーフへ進むことはない)
  - 挿入・更新・削除が 1 つのリーフノードに収まるなら、これで完了する
- 悲観
  - 楽観で降りた結果、分割やマージが必要と分かったら、保持しているラッチをいったん解放し、B+Tree レベルの SX を取り直してから降り直す
  - 構造変更中も探索や楽観更新は並行して降りられる。変更対象の各ページには Exclusive を取って書き換えるため、その対象ページに到達した操作だけが待機する
- 2 段にする理由
  - 構造変更は稀なので、すべての更新で最初から B+Tree レベルの SX を取ると、更新同士が直列化して並行性を損なう
  - そのためまず楽観で試し、必要なときだけ悲観へ切り替えることで、大半の更新を並行で処理可能にする

## 順次走査

- 範囲スキャンや全件スキャンは、最初の検索で 1 つのリーフに位置を定め、リーフの連結リストを左から右へ辿りながらレコードを順に読み進める
- ラッチは 1 レコードを読み出す瞬間だけ短期の Shared を取り、読み出し後すぐ解放する
- そのため走査の合間 (ラッチを解放している間) に、他の操作が分割やマージで当該リーフの内容や境界を変えうる
- この問題には以下の方針で対応する
  - バッファページが持つ[更新カウンタ](../buffer/buffer-pool.md)を記憶しておき、ラッチを取り直したときにカウンタを比べて、手放していた間にページが変わったかを確認する
  - 変わっていなければ記憶した位置のまま続行する
  - 分割やマージで実際に変わっていた場合だけ、直前に読んだレコードのキーで位置を取り直す
