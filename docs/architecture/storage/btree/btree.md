# B+Tree

## 概要

- 参考
  - [MySQL with InnoDB のインデックスの基礎知識とありがちな間違い](https://techlife.cookpad.com/entry/2017/04/18/092524)
  - [インデックスの役割と構成](https://qiita.com/immrshc/items/6cdb47f61e10de8ee1a5)
- B+Tree の[ノード](./node.md)はページ単位
- B+Tree 全体はあくまで構造 (抽象) にすぎず、B+Tree 内のノード (=ページ) がバッファプールに格納されているのか、ディスクに格納されているのかという情報は関与しない
- B+Tree のリーフノードは双方向連結リストになっているため、全件スキャンや範囲検索などで、容易に (効率的に) リーフノードを走査することができる

## B+Tree の作成

- 新しい B+Tree を作成する際は、まず空の[リーフノード](./node-leaf.md)を 1 つ作成し、そのノードをルートノードとして設定する
- また[メタページ](./meta-page.md)も作成し、ルートノードのページ ID をメタページに保存する

## ノードの検索

1. 目的のリーフノードに到達するまで、二分探索で[ブランチノード](./node-branch.md)を辿る
2. リーフノード内を二分探索する

### 検索の 2 種類

検索は、リーフノード内での着地位置の解釈の仕方によって 2 種類に分かれる

- 最初の候補位置を返す検索 (lower bound)
  - 指定キー以上の最初のレコードに着地し、そこから走査を始める
  - 範囲検索や prefix scan、走査開始位置の決定に用いる
  - キーが存在しない場合は「次に大きいキー」のレコードに着地するため、着地したレコードのキーが指定キーと一致するとは限らない
- 完全一致を要求する検索
  - lower bound の結果に対して、着地したレコードのキーが指定キーと一致することを追加で確認する
  - 一致しなければ「キーは存在しない」として扱う
  - UNIQUE 制約の重複チェック、外部キーの子側から親レコードを引く検索、プライマリキーによる単一行取得に用いる

下位レイヤーのノード走査ロジックは lower bound だけを提供し、完全一致が必要な経路は呼び出し側で一致確認を行う

### 例

_key = "grape" を検索_

- B+Tree の構造:

    ```txt
                [Root: Branch Node]
                Records: [(key="fish", pageId=10), (key="monkey", pageId=20)]
                RightChild: pageId=30
                       /            |              \
                  (<fish)       (fish~monkey)    (>=monkey)
                  PageID=10       PageID=20       PageID=30
                    /                |                \
     [Leaf: apple,cat,dog]  [Leaf: fish,grape,human]  [Leaf: monkey,tiger,zebra]
    ```

1. ルートノード (ブランチノード) で二分探索
   - "grape" と "fish" を比較 → fish < grape
   - "grape" と "monkey" を比較 → grape < monkey
   - → インデックス 1 のレコード (key="monkey", pageId=20) を取得

2. 子ページ (PageID=20) を取得して探索

3. リーフノードで二分探索
   - "grape" と "fish" を比較 → fish < grape
   - "grape" と "grape" を比較 → 一致
   - → インデックス 1 のレコード (key="grape") を取得して返す

## 非キーの更新

- 更新前後でキーの値は変わらないと仮定する
- 更新後レコードがリーフノードの空きに収まる場合は、非キー領域のリサイズによって同じ位置で更新する
  - 参照: [リーフノードのレコードの非キーを更新](./node-leaf.md#レコードの非キーを更新)
- 収まらない場合は悲観モードに切り替え、対象レコードをリーフノードから削除してから、更新後レコードを挿入する
  - キーは不変のため、挿入は削除したレコードと同じリーフ領域に入る
  - 容量によっては通常の[レコード挿入](./btree-insert.md)と同じ分割が起こる。リーフノードの分割やルートノードの分割が発生した場合の[メタページ](./meta-page.md)の更新も挿入と同じ規則に従う
  - 削除直後のアンダーフロー処理 (兄弟ノードからの転送やマージ) は行わず、一時的なアンダーフローを許容する (直後の挿入が同じリーフ領域を埋めるため)
- 更新後レコードが 1 レコードの最大サイズ (ノード容量の半分からポインタ分を引いたもの) を超える場合は、削除を行う前にエラーとする
  - 削除した後に挿入が失敗するとレコードが消失するため、サイズの検証は必ず削除より前に行う
