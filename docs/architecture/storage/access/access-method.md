# アクセスメソッド

## 概要

- データ構造を辿って要求に応じたデータ操作を行う
  - 実際のデータの読み書きはバッファプールに依頼する
- アクセスメソッドのデータ構造とアルゴリズムには [B+Tree](../btree/btree.md) を使用

## テーブル

- テーブルに対して 1 つの `${table_name}.db` ファイルが存在する
- 1 つのテーブルには 1 つのプライマリインデックスと複数のセカンダリインデックスが存在する (セカンダリインデックスは存在しない場合もある)

### プライマリインデックス

- プライマリインデックスはクラスタ化インデックスとする
- テーブルの実態は、プライマリキーをキー領域、その他カラム値を非キーフィールドとするレコード (後述)
- プライマリキーが複合キーの場合も考慮して、複合キーの場合も正しくソートされるように [Memcomparable format](../encode/memcomparable-format.md) を使用してプライマリキーをエンコードする

### セカンダリインデックス

- 非 UNIQUE インデックスにも対応可能にするため、セカンダリインデックスのキーは `セカンダリキー + プライマリキー` の構成にしている
  - (B+Tree のキーに対して一意制約を設けた方が実装が楽なため)
- B+Tree のソート順は (セカンダリキー, プライマリキー)
- 検索の際は、まずセカンダリインデックスを検索し、その後必要があればキー領域に含まれるプライマリキーを使用して、プライマリインデックスを辿ることでレコード情報を取得する

## レコード

- B+Tree の[レコード](../btree/node.md#レコード)はヘッダー領域・キー領域、非キー領域の 3 領域で構成される
- アクセスメソッドは、それらの領域をインデックスの種類に応じて以下のように意味づける
- B+Tree のソートはキーに基づいて行われる
- レコードはそれぞれ「どこからどこまでがキーか」という情報を持っているため、それに基づいてソート順が決定される

#### プライマリインデックス

| 領域 | フィールド | バイト数 | 説明 |
| --- | --- | --- | --- |
| ヘッダー | DeleteMark | 1 | 削除マーク |
| キー | プライマリキー | 可変 | プライマリキーのカラム値をエンコードしたもの |
| 非キー | lastTrxId | 4 | このレコードを最後に INSERT/UPDATE したトランザクション ID |
| 非キー | rollPtr | 6 | undo ログレコードへのポインタ (ページ番号 4B + オフセット 2B) |
| 非キー | 非キーカラム | 可変 | プライマリキー以外のカラム値をエンコードしたもの |

#### セカンダリインデックス

| 領域 | フィールド | バイト数 | 説明 |
| --- | --- | --- | --- |
| ヘッダー | DeleteMark | 1 | 削除マーク |
| ヘッダー | lastTrxId | 4 | このレコードを最後に INSERT/UPDATE/DELETE したトランザクション ID |
| キー | セカンダリキー | 可変 | セカンダリインデックスを構成するカラム値をエンコードしたもの |
| キー | プライマリキー | 可変 | プライマリキーを構成するカラム値をエンコードしたもの |
| 非キー | - | 0 | 非キー領域は使用しない。セカンダリキーとプライマリキーの境界はインデックスメタデータの SK カラム数から判別できる |

※ セカンダリインデックスの lastTrxId は、セカンダリインデックスのみで完結する読み取り (Covering Index) の MVCC 可視性判定で使用する (詳細: [MVCC - セカンダリインデックス経由の可視性判定](./mvcc.md#セカンダリインデックス経由の可視性判定))

## テーブル作成と既存テーブル open のライフサイクル

テーブル作成では、以下の順序で永続物を作る

1. テーブル本体の `${table_name}.db` ファイルを作成する
2. プライマリインデックスの B+Tree (メタページと空のルートリーフ) を `${table_name}.db` 内に作成する
3. カタログのテーブル定義・カラム定義に新テーブルを登録し、プライマリインデックスのメタページ位置を記録する
4. セカンダリインデックスがある場合は、各セカンダリインデックスの B+Tree を作成し、カタログのインデックス定義に登録する
5. 外部キー制約がある場合は、カタログの制約定義に登録する

既存テーブルを open するときは、カタログからメタデータを読み出し、各 B+Tree のメタページ位置を解決する。永続物の作成は伴わない

これらの永続物の作成手順は単一の mini-transaction にまとめられているわけではないため、途中でクラッシュした場合、ファイルだけ作られてカタログ登録が行われていない、もしくはプライマリインデックスは登録済みでセカンダリインデックスは未登録、といった中間状態が残り得る

この中間状態は [DDL](./ddl.md) の枠組みで取り消す。テーブル作成は単一の DDL 操作として扱われ、各永続操作 (物理ファイル確保 / B+Tree 作成 / カタログ登録) の取消情報を DDL Undo として専用領域に書き出す。途中でクラッシュした場合は再起動時のリカバリで [未完了 DDL のロールバック](./crash-recovery.md#3-未完了-ddl-のロールバック) フェーズが DDL Undo を逆順に適用し、テーブル作成は完了するか完全に取り消されるかのいずれかに収束する (= 全か無かの原子性保証)

## 操作

### レコードの挿入

- プライマリインデックスの B+Tree にレコードを挿入
  - 同一プライマリキーのレコードがすでに論理削除済み (DeleteMark=1) の場合はそのレコードを上書きし、DeleteMark を 0 に戻す
- セカンダリインデックスにも同様に挿入する (UNIQUE インデックスであれば、重複確認を行う)
- 外部キーチェック
  - 該当テーブルが FK を持つ場合、挿入する値が参照先テーブルに存在するかを確認し、存在しない場合はエラーとする

### レコードの削除

- レコードを論理削除 (DeleteMark=1) する
- 物理削除は後でパージによって行われる
- プライマリインデックス: レコード内の DeleteMark を 1 に更新
- セカンダリインデックス: レコード内の DeleteMark を 1 に更新
- レコードの検索時には、DeleteMark = 1 のレコードをスキップする
- 外部キーチェック
  - 該当テーブルが親テーブルとして参照されている場合、削除する値で参照元テーブルを検索し、参照されている場合はエラーとする

### レコードの更新

- プライマリインデックスにおけるレコードの更新はインプレース更新で行う
  - プライマリキーが変わる場合は、論理削除 + 挿入として処理する
- セカンダリインデックスにおけるレコードの更新は、インデックスを構成するカラムの値が変更される場合のみ、論理削除 + 挿入で実現する
  - インデックスを構成するカラムが更新対象に含まれない場合は何もしない
- 外部キーチェック (FK に関係するカラムが更新対象に含まれる場合のみ実行):
  - 該当テーブルが親テーブルとして参照されている場合、旧値で参照元テーブルを検索し、参照されている場合はエラーとする
  - 該当テーブルが FK を持つ場合、新値が参照先テーブルに存在するかを確認し、存在しない場合はエラーとする
- プライマリキー更新により論理削除 + 挿入に分岐する場合は、それぞれの操作内で外部キーチェックが行われる

### 外部キーチェックの対応範囲

外部キー制約の検査は以下の範囲に限定する

- 参照先 (親テーブル) は、親テーブルのプライマリキーとして検索する。任意の UNIQUE キーを参照先とする FK には対応しない
- 子側 (FK を持つテーブル) では、FK カラムがセカンダリインデックスの先頭カラムとして登録されている必要がある。先頭カラムがセカンダリキーになっていない FK 検索や、複数カラムにまたがる FK は対応しない
- 検査はレコードの挿入 / 削除 / 更新の各操作内で行い、違反時はエラーとして操作全体を失敗させる

### 外部キーチェックの並行制御

子側 INSERT / UPDATE と親側 DELETE / UPDATE は、相手のトランザクションが進行中の場合に直列化される

- 子側 INSERT / UPDATE: 参照先の親レコード (プライマリキー単位) に対して共有ロックを取得する。並行する親側 DELETE / UPDATE が完了するまで待ち、それから親レコードの存在を確認する
- 親側 DELETE / UPDATE: 参照元 (子テーブル) のセカンダリインデックスを prefix scan した結果の各レコードに対して、親トランザクションの共有ロックを取得する。子側で進行中の論理削除 / 更新が完了するまで待ち、ロック取得後に最新のレコード状態を再評価して FK 違反の有無を判定する
- どちらの方向の共有ロックも Strict 2PL により、トランザクション完了 (COMMIT / ROLLBACK) で一括解放される
- 範囲ロック (gap lock 相当) は導入しない。並行する子側 INSERT による新規子行の出現は MVCC の Read View で扱う

#### セカンダリインデックスの更新について

- セカンダリインデックスのキー領域は `セカンダリキー + プライマリキー` で構成されるため、論理削除後に同じセカンダリキーで新しいレコードを挿入しても、B+Tree 上のキー重複は起こらない
- テーブル `users (id PK, name, email UNIQUE)` で `email = 'alice@example.com'` の行の `id` を `1` → `2` に更新する場合の更新の流れは以下のようになる
  1. 論理削除: `key=(alice@example.com, 1)` の DeleteMark を 1 にセット
  2. 挿入: `key=(alice@example.com, 2)` を DeleteMark 0 で挿入
- ユニーク制約のチェックはセカンダリキー部分 (`alice@example.com`) のみに対して行い、また論理削除済みのレコードはスキップする

#### ユニークセカンダリインデックスの並行制御

ユニーク制約付きのセカンダリインデックスでは、行キー (セカンダリキー + プライマリキー) 単位のロックだけでは、同じセカンダリキーで異なるプライマリキーを持つ並行 INSERT を直列化できない。これを直列化するため、ユニークインデックスに限ってセカンダリキー単位の追加ロックを取る

- INSERT 時にユニーク制約の重複確認を行う直前に、対象セカンダリキー単位の排他ロックを取得する
- 論理削除でも同じく対象セカンダリキー単位の排他ロックを取得する (SK 変更を伴う UPDATE は論理削除 + 挿入の組み合わせで実現するため、結果として双方で取得される)
- 追加ロックは Strict 2PL に従い、トランザクション完了 (COMMIT / ROLLBACK) で解放される
- 非ユニークインデックスではこの追加ロックを取らない (重複が許容されるため、衝突する操作同士が直列化される必要がない)
- 追加ロックを取らない場合に起こりうる事象は、別トランザクションの未コミット論理削除と並行する INSERT が同じセカンダリキー値を取り、コミット直後に重複が観測されるケース。SK 単位の追加排他ロックにより、双方が同時に進行することを防ぐ
- 範囲ロック (gap lock 相当) は導入しない。範囲を越えた phantom は MVCC の Read View で防ぐ
