# ページクリーナー

## 概要

- データ変更によって生じたダーティーページを定期的にディスクにフラッシュする仕組み
- トランザクションごとにディスクへのフラッシュを行うわけではなく、ページクリーナーが特定のタイミングでフラッシュを行う
- これにより、(複数のトランザクションで) 同じページに対して複数回の更新があった場合に 1 回のフラッシュで済むため、ディスク I/O を削減できる

## フラッシュリスト

ページクリーナーがどのページをフラッシュすべきかを管理するために、バッファプール内にフラッシュリストを持つ

- ページが最初にダーティーになった時点でフラッシュリストに追加する
- すでにフラッシュリストに含まれるページがサイド変更された場合は追加しない
- フラッシュリストはダーティーになった順に並んでおり、古いものほどリストの先頭に位置する
- ページがフラッシュされたらフラッシュリストから除外する

この順序管理により、ページクリーナーは古いダーティーページから優先的にフラッシュでき、[チェックポイント LSN](./checkpoint.md#チェックポイント-lsn) を効率的に進めることができる

## フラッシュの流れ

1. フラッシュリストの先頭 (最も古いダーティーページ) から順にフラッシュ対象を選択する
2. Redo ログを Redo ログファイルにフラッシュする
   - WAL 原則に従って、データページより先に Redo ログをフラッシュすることで、ディスク上のページが Redo ログより新しくなることを防ぐ
3. 対象のデータページをディスクに書き出し、フラッシュリストから除外する

## 動作方式

ページクリーナーはバックグラウンド goroutine として動作し、1 秒間隔で閾値チェックを行う

- サーバー起動時に goroutine を起動し、シャットダウン時に停止する
- SQL 実行とは独立して動作するため、トランザクションの COMMIT/ROLLBACK に依存しない
- 閾値を超えている場合、フラッシュリストの 1/4 (最低 1 ページ) をフラッシュする

## フラッシュの閾値

以下のいずれかの閾値を超えた場合にフラッシュを実行する

- Redo ログのサイズ (ファイルサイズ + バッファサイズ) が 1MB を超えた場合
- ダーティーページ率 (フラッシュリストのサイズ / バッファプールの最大サイズ * 100) が 90% を超えた場合
