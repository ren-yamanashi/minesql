# DDL

## 参考文献

- [Atomic DDL - MySQL 8.0 Reference Manual](https://dev.mysql.com/doc/refman/8.0/en/atomic-ddl.html)
- [Atomic Data Definition Statement Support in MySQL 8.0](https://dev.mysql.com/blog-archive/atomic-ddl-in-mysql-8-0/)

## 概要

- DDL (Data Definition Language) は、テーブル・インデックス・制約といったスキーマオブジェクトを生成・破棄するための操作の総称
- minesql における DDL は Atomic な挙動を保証する。完了するか、完全に取り消されるかの二択であり、中間状態がディスク上に残らない
  - 永続物が一部だけ作られた状態 (孤児化したファイル、半端な B+Tree、メタテーブルへの部分登録) はクラッシュリカバリで取り消され、再起動後の整合性を保つ
- 同時に複数の DDL が走ることは想定しない。DDL は autocommit (1 操作 = 1 トランザクション) として扱い、並行 DDL は構造上発生しない前提で設計を簡素化する
- DDL の責務は、論理的には「物理ファイルの確保」「B+Tree の作成」「カタログのメタテーブルへの登録」の 3 種の永続操作の組み合わせとして整理できる

## DDL の構成要素

1 つの DDL 操作 (例: テーブル作成) は、以下のいずれか/複数の永続操作の組み合わせとして構成される

| 構成要素 | 内容 |
| --- | --- |
| 物理ファイル確保 | テーブル本体の `${table_name}.db` ファイルを新規生成し、対応する FileId を払い出す |
| B+Tree 作成 | プライマリインデックス・セカンダリインデックスの B+Tree (メタページとルートリーフ) を該当ファイル内に構築する |
| カタログ登録 | テーブルメタデータ・インデックスメタデータ・インデックスキーカラムメタデータ・カラムメタデータ・制約メタデータの各 B+Tree にレコードを追加する |

これらは単一の mini-transaction にまとまるわけではなく、複数のページ変更・複数のファイル操作にまたがる。クラッシュは任意の境界で発生しうるため、中間状態を取り消す仕組みが必要になる

## DDL 専用予約トランザクション ID

minesql のトランザクション ID は用途別に 4 種類の値域に分かれる

| 種別 | 用途 |
| --- | --- |
| ユーザー採番 ID | 通常のユーザートランザクション。Begin で単調増加に動的に払い出される |
| システム予約 ID | 起動時の永続オブジェクト初期化や、単発のカウンタ更新 (永続値書き込み) で使う固定値。DDL 予約 ID とは責務が異なり、DDL Undo は書かない |
| パージ予約 ID | バックグラウンドで動作する物理削除処理 ([パージ](./purge.md)) で使う固定値 |
| DDL 予約 ID | DDL 操作で使う固定値。物理ファイル確保・B+Tree 作成・カタログ登録のすべてが、この ID 配下のトランザクションで実行される |

4 種は互いに重ならない値域を持つ。これにより、Redo / Undo に書かれたレコードの所有者を一意に判定できる

DDL 予約 ID を単一値とできるのは、minesql が並行 DDL を想定しないため。DDL は autocommit で実行され、Begin と Commit がユーザー操作の境界と切り離されており、1 つの DDL 操作の中で完結する

### DDL トランザクションを介した各 step へのリソース提供

DDL 予約 ID で実行されるトランザクションは、ユーザー採番のトランザクションと同じトランザクションオブジェクトとして払い出される。DDL 操作は autocommit のため、DDL 開始時に DDL 予約 ID でトランザクションを払い出し、完了境界 (COMMIT / ROLLBACK) で同じトランザクションを終了させる。これにより、ストレージ層リソース (バッファプール、Redo ログ、Undo ログ、カタログ) への参照は DDL トランザクションが内部に集約する

DDL を構成する各 step (物理ファイル確保、B+Tree 作成、カタログ登録) は、いずれも DDL トランザクションを引数で受け取り、ストレージ層リソースへのアクセスはトランザクションから引き出して行う。step ごとに必要なリソース参照を個別に渡し直す経路は持たない。これにより、DDL 操作全体がコンテキストオブジェクトとしての DDL トランザクション配下で一貫して実行され、step 境界でリソースの引き回しを誤る余地が生じない

ROLLBACK 経路の DDL Undo 逆適用も同じ DDL トランザクションを引数で受け取り、Undo の各エントリへの逆操作を同じトランザクション配下で実行する

## DDL Undo の役割と専用領域

DDL は通常の Undo とは別系統の Undo (以下「DDL Undo」) を専用領域に書き出す。専用領域はカタログ初期化時に確保され、サーバライフタイム中ずっと残る永続コンテナとして扱う。各 DDL はこの永続コンテナにエントリ列を積み上げ、DDL 完了 (COMMIT / Rollback) 時にコンテナの中身 (= エントリ列) のみを物理破棄する。コンテナ自体は破棄せず、次の DDL がそのまま再利用する。通常 Undo と分離する理由は責務と寿命が異なるため

| 観点 | 通常 Undo | DDL Undo |
| --- | --- | --- |
| 主用途 | Rollback と MVCC の旧バージョン管理 | DDL Rollback のみ |
| 寿命の決定 | コミット後も他トランザクションの ReadView から参照される可能性がある間は保持 (パージ経路で回収) | DDL 完了 (COMMIT) 時にコンテナの中身 (= エントリ列) を即時物理破棄、コンテナ自体は永続 |
| 並行アクセス | 任意数のユーザートランザクションが同時に書き込む | 並行 DDL は想定せず、1 つの DDL が逐次的に書き込む |
| クラッシュ後の処理 | リカバリで未完了トランザクションを Undo 逆適用 | リカバリで未完了 DDL を専用領域から逆順に Undo 適用 |

DDL Undo が MVCC に関与しないのは、DDL の対象がデータ行ではなくスキーマオブジェクトのため。スキーマオブジェクトには旧バージョンとして「未完成のテーブル」を見せる意味がなく、Consistent Read の対象にもならない

専用領域に分離することで、ライフサイクルの異なる 2 系統の Undo を独立して扱える。通常 Undo の History List やパージ経路に DDL Undo が混ざらないため、パージは「ユーザートランザクションがいつ参照しなくなるか」の判定だけに集中できる

## DDL Undo の種類

DDL 中の永続操作 3 種に対応して、DDL Undo にも 3 種類の取消情報が存在する

| 種類 | 取消対象 | Rollback 時の論理 |
| --- | --- | --- |
| B+Tree 解放 Undo | 新規作成された B+Tree | B+Tree のメタページから走査して全ページを解放する |
| メタテーブル削除 Undo | カタログメタテーブルへの 1 レコード追加 | 該当メタテーブルから当該レコードを物理削除する |
| 物理ファイル削除 Undo | 新規確保された FileId とそれに対応する物理ファイル | バッファプール内の該当ページを追い出した上で、物理ファイルを削除する |

各 Undo は、それぞれの永続操作が成功した直後に DDL Undo 専用領域へ書き込まれる。1 つの DDL 操作 (例: セカンダリインデックス付きテーブルの作成) は、複数種・複数件の DDL Undo を順に積み上げることで構成される

FileId / インデックス ID のカウンタ自体は単調増加させたまま据え置き、ロールバックで巻き戻さない。同じ ID 値を再利用しないことで、ロールバック後に同じ ID が別の用途に再割り当てされる事故を避ける

## DDL 中のクラッシュ挙動

DDL 中のクラッシュは、永続操作のどの境界でも発生しうる。クラッシュ後の再起動時には、未完了 DDL に対応する DDL Undo が専用領域に積まれた状態で残っている

DDL 中のクラッシュは概念的に以下のいずれかの中間状態を作る

- 物理ファイルだけ作られ、B+Tree もカタログ登録もない
- B+Tree の一部 (メタページのみ、もしくはルートリーフまで) が作られ、カタログ登録がない
- プライマリインデックスは登録済みだが、セカンダリインデックスやその登録が未完
- 制約メタデータの一部だけ登録されている

いずれの中間状態も、DDL Undo を逆順に適用することで「DDL 開始前の状態」に戻る。具体的には、後から積まれた Undo (例: 制約登録の取消) から先に適用し、最後に物理ファイル削除に至る

完了せずに残った DDL は、Redo に COMMIT レコードが到達していないことで識別される。これは通常のユーザートランザクションと同じ完了判定と整合する

## DDL の完了処理

DDL 操作の COMMIT 時には、以下が行われる

1. Redo ログに COMMIT レコードを追加し、フラッシュする (永続化境界)
2. DDL Undo 専用領域コンテナの中身 (= 積まれた Undo エントリ列) を、即時に物理破棄する。コンテナ自体は永続のまま残し、次の DDL がそのまま再利用する

DDL Undo はパージ経路を通らない。MVCC 用に旧バージョンとして参照される可能性がないため、コミット直後に解放しても整合性が壊れない。Undo を保持し続けるコストとリカバリ走査コストの両方を回避できる

破棄が完了する前にクラッシュした場合は、Redo の COMMIT レコードが既に到達しているため、リカバリは当該 DDL を「完了済み」と判定し、DDL Undo を Rollback 対象から除外する。残っている Undo エントリは次回のリカバリ完了時にコンテナの中身としてクリアされ、過去の完了 DDL が誤って Rollback されることはない

## クラッシュリカバリでの位置づけ

[クラッシュリカバリ](./crash-recovery.md) の流れに、DDL Undo の Rollback が追加される

1. Redo ログの適用
2. 通常 Undo の Rollback (未完了ユーザートランザクション)
3. DDL Undo の Rollback (未完了 DDL)
4. リカバリ完了処理 (全ダーティーページのフラッシュ + Redo クリア)

通常 Undo の Rollback と DDL Undo の Rollback は別フェーズとして実行する。通常 Undo の Rollback ではテーブルが存在することを前提に行を巻き戻す一方、DDL Undo の Rollback ではテーブル自体を消す可能性があるため、順序を入れ替えるとユーザートランザクションの巻き戻しが消えたテーブルに対して走る事故が起こりうる。先にユーザートランザクションを巻き戻すことでこの矛盾を避ける

## InnoDB との対応

minesql の DDL 設計は、InnoDB 8.0 以降の Atomic DDL と概念対応している

| minesql の概念 | InnoDB の対応概念 |
| --- | --- |
| DDL 専用予約トランザクション ID | DDL 用のシステム内部トランザクション |
| DDL Undo 専用領域コンテナ (永続) | `mysql.innodb_ddl_log` 表 (システムテーブル、サーバライフタイム中永続) |
| コンテナへの 1 エントリ追加 | `mysql.innodb_ddl_log` への 1 行 INSERT |
| B+Tree 解放 Undo | DROP エントリ (テーブル/インデックス削除) |
| 物理ファイル削除 Undo | DELETE_SPACE エントリ (テーブルスペース削除) |
| DDL COMMIT 時のコンテナ中身破棄 | DDL log エントリ行の DELETE (テーブル自体は残す) |
| リカバリでの DDL Undo の Rollback | Server 起動時の DDL log apply フェーズ |

minesql は学習目的のため InnoDB のすべての DDL ステートメント (RENAME・ALTER・CREATE INDEX 等) を扱うわけではない。設計上は同じ枠組み (専用 trxId + DDL Undo 3 種 + 専用領域) で他の DDL も追加可能な構造を取る
