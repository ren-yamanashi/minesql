# クラッシュリカバリ

## 概要

- サーバーを正常終了した場合、すべてのダーティーページをバッファプールからディスクにフラッシュするのを待機してから終了する
  - サーバー終了時にコミットされていなかったトランザクションはロールバックされる
  - ただし正常終了処理は現時点では未実装 (サーバー層が未移植のため)
- 従って、正常終了している限りは、それ以前のコミットはすべてディスクに同期されたクリーンな状態になる
- 逆に、異常終了した場合は、ダーティーページの存在を留意する必要がある
- これをケアするための異常終了直後の起動時に走るディスクファイルに整合性を戻すための処理を「クラッシュリカバリ」と呼ぶ

## 流れ

異常終了の再起動時、以下の流れでデータの整合性を復元する

### Pin とラッチの扱い

- Redo ログ適用と Undo ログ走査でも、通常の操作と同様に [mini-transaction](../buffer/latch.md) でページの Pin とラッチを束ねて管理する
- リカバリは単一スレッドだが、Pin の解放点を「ページごとの 1 適用」「Undo ページごとの 1 走査」に集約することで、Pin の所有が操作単位で追える状態を保つ

#### 1. Redo ログの適用

- Redo ログのチェックポイント LSN 以降のレコードをスキャンし、記録された変更をページに再適用する
- コミット済みか未コミットかを問わず、すべてのレコードを対象とする
- [Page LSN](../log/redo.md#page-lsn) を参照し、適用済みのレコードはスキップする
- 複数ページを変更する操作 ([mini-transaction](../log/redo.md#mini-transaction-の区切り)) は、終わりの区切りまで揃ったものだけを適用する
  - クラッシュで末尾が途中までしか書かれていない mini-transaction は破棄して適用しない
  - これにより、複数ページにまたがる構造変更が「一部のページだけ適用された」半端な状態にならない
  - mini-transaction の途中でページの所有を個別に解放するケースでは、解放されたページが終端の区切りより前にディスクへフラッシュされる可能性がある。この場合でも次の組み合わせでリカバリ時に整合性が取れる
    - 各ページの変更を Redo に記録するときに [Page LSN](../log/redo.md#page-lsn) をスタンプし、ディスクに先行フラッシュされたページとそれに対応する Redo レコードの位置関係を一意に対応付ける
    - データページのフラッシュは WAL 原則に従って先行 Redo フラッシュを行うため、ディスクに反映された変更に対応する Redo は必ず先にディスクに書かれている
    - 終端の区切りが書かれていない mini-transaction を不完全とみなして破棄する一方で、Page LSN を参照して既に適用済みのレコードはスキップするため、リカバリは「ディスクの状態」と「適用すべき Redo」を一致させる方向に動く

#### 2. 不完全なトランザクションのロールバック

- Redo ログ内の COMMIT または ROLLBACK レコードの有無で、各トランザクションが完了済みかどうかを判定する
- どちらのレコードもないトランザクションは未完了と判定し、Undo ログを逆順に適用してロールバックする
- Undo ページ自体も [1](#1-redo-ログの適用) のフェーズで復元されているため、Undo ログを使用できる
- このフェーズで取り消すのはユーザートランザクションと、パージ予約 ID / DDL 予約 ID 配下で通常 Undo を書いたトランザクション。DDL 専用領域に書かれた [DDL Undo](./ddl.md#ddl-undo-の役割と専用領域) は次のフェーズで取り扱う

#### 3. 未完了 DDL のロールバック

- DDL 予約 ID で実行された DDL のうち、Redo ログに COMMIT レコードが到達していないものを未完了と判定する
- DDL Undo の専用領域から、未完了 DDL に対応する Undo レコードを逆順に読み出し、各種類に応じた逆操作を適用する (B+Tree 全ページ解放 / メタテーブルからの物理削除 / 物理ファイル削除)
- 通常 Undo の Rollback と別フェーズに分けるのは順序保証のため。通常 Undo 適用はテーブルが存在することを前提に行を巻き戻すのに対し、DDL Undo の取消はテーブル自体を消す可能性があり、順序を入れ替えるとユーザートランザクションの巻き戻しが消えたテーブルに対して走る矛盾が生まれる
- 適用後に残った当該 DDL の DDL Undo は専用領域から物理破棄する (詳細: [DDL](./ddl.md#クラッシュリカバリでの位置づけ))

#### 4. リカバリ完了処理

- REDO 適用と通常 Undo / DDL Undo の Rollback が完了した後、バッファプール上の全ダーティーページをディスクへフラッシュし、続けて Redo ログを全レコード破棄してクリアする
- この一連の処理によって、「リカバリ完了直後のディスク状態」は「サーバーが正常終了したときの状態」と論理的に同じ意味を持つ
  - 次回起動時には Redo ログにレコードが残っていないため、リカバリは何もする必要がなく、通常起動に進める
- リカバリ完了処理の途中でクラッシュしても問題ない
  - 全ダーティーページのフラッシュは何度実行しても同じ結果になるため再実行で復元される
  - Redo ログのクリアが完了していなければ、次回起動時に再度 REDO 適用と UNDO ロールバックから再実行され、最終的に同じ完了状態へ収束する (idempotent)

### ケースごとの挙動

#### コミット済みの変更がディスクに反映されている場合

- データページは最新の状態でディスクにある
- Step 1: Redo ログを適用するが、Page LSN により既に適用済みと判定されスキップされる
- Step 2: COMMIT レコードがあるためロールバック対象にならない
- 結果: 変更は保持される (何もする必要がない)

#### コミット済みの変更がメモリにしかない場合 (ダーティーページ)

- データページはディスク上では変更前の状態
- Step 1: Redo ログを適用し、コミット済みの変更をデータページに復元する
- Step 2: COMMIT レコードがあるためロールバック対象にならない
- 結果: 変更は Redo ログから復元され保持される

#### 未コミットの変更がディスクに反映されている場合

- バッファプールの都合でダーティーページがフラッシュされ、未コミットの変更がディスクに書かれている
- Step 1: Redo ログを適用するが、Page LSN により既に適用済みと判定されスキップされる
- Step 2: COMMIT レコードがないため未完了と判定され、Undo ログを逆順に適用してロールバックする
- 結果: 未コミットの変更は取り消される

#### 未コミットの変更がメモリにしかない場合 (Redo ログもデータページも未フラッシュ)

- データページも Redo ログもディスクには書かれていない
- クラッシュすると全てメモリごと消える
- 結果: リカバリで何もする必要がない。ディスク上は変更前の状態のまま

#### 未コミットの変更がメモリにしかないが、Redo ログだけはディスクにフラッシュされている場合

- Redo ログは COMMIT 時以外にも、ログバッファの上限超過時の自動フラッシュやページクリーナーのダーティーページフラッシュ前 (WAL 原則による先行フラッシュ) で永続化されうる。このため、未コミットでも Redo ログだけは先にディスクへ到達している場合がある
- データページはまだディスクに反映されていない
- Step 1: Redo ログを適用し、未コミットの変更をデータページに復元する
- Step 2: COMMIT レコードがないため未完了と判定され、Undo ログを逆順に適用してロールバックする (= 「未コミットの変更がディスクに反映されている場合」と同じ経路で取り消される)
- 結果: 一旦復元されたうえでロールバックされ、変更前の状態に戻る

## 予約トランザクション ID の扱い

ユーザートランザクションとは別に、以下の 4 種類の予約トランザクション ID が存在する (詳細: [トランザクション - 予約トランザクション ID](./transaction.md#予約トランザクション-id))

- システム予約 ID: 起動時の永続オブジェクト初期化や、単発のカウンタ更新で使う
- パージ予約 ID: [パージ](./purge.md#クラッシュ耐性) のバックグラウンド物理削除に使う
- DDL 予約 ID: [DDL](./ddl.md) で実行される DDL 操作に使う

いずれもユーザー採番と衝突しない値をそれぞれ確保し、互いにも異なる値を割り当てる

- いずれも通常のトランザクション ID と同じ扱いでリカバリを通す
- 未完了 (COMMIT/ROLLBACK レコードなし) であれば、通常のトランザクション ID と同様にロールバック対象に含める
- DDL 予約 ID のトランザクションが書いた DDL Undo は専用領域に書かれており、[未完了 DDL のロールバック](#3-未完了-ddl-のロールバック) フェーズで逆順に適用される。これにより DDL 中のクラッシュで生じた中間状態 (孤児ファイル / 半端な B+Tree / 部分登録されたメタテーブル) が取り消される
- Undo レコードを持たない起動時初期化やパージは、ロールバック対象に含まれても実体としては何もしない (= idempotent な再実行で復元可能)

## リカバリ中のロールバック経路と Redo

未完了トランザクションに対する Undo 逆適用 (= [リカバリ中のロールバック](./transaction.md#通常運用時とリカバリ中の差)) は、通常運用時のロールバックと同じ Undo 逆適用ロジックを共有するが、Redo には何も記録しない

- リカバリは終了時にチェックポイント相当の操作で過去の Redo を切り詰めるため、リカバリ中の変更を再度 Redo に書く意味がない
- リカバリ中の Undo 逆適用を Redo に書き戻すと、次回起動時のリカバリで同じ変更を二重に適用する経路が生まれる可能性がある (idempotent 性を強く保つために避ける)
- 通常運用時の呼び出し側は、ロールバック対象のトランザクション ID で書き込み用の mini-transaction を作る。リカバリ中の呼び出し側は、Redo を伴わない読み取り用の mini-transaction を作って同じ Undo 逆適用ロジックを呼ぶ
