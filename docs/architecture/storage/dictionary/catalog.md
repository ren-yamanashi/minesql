# カタログ

## 概要

- テーブルのメタデータ (テーブル名、カラム情報、インデックス情報など) を管理する
- カタログは、実データファイル (`${table_name}.db`) とは別のファイルに保存される
  - MySQL v8.0 以降でいうところのデータディクショナリテーブル (`mysql.ibd`)
- カタログは以下の 6 つの B+Tree で構成される
  - テーブルメタデータ
  - インデックスメタデータ
  - インデックスキーカラムメタデータ
  - カラムメタデータ
  - 制約メタデータ
  - ユーザーメタデータ

### ヘッダーページ

- カタログファイルの page 2 をヘッダーページとしている
  - page 0 は全ファイル共通の FSP ヘッダー、page 1 は最初の inode ページが占めるため (詳細: [ファイル空間管理 - 予約ページマップ](../fsp/fsp.md#予約ページマップ))
- ヘッダーページはカタログヘッダー segment の最初のページとして確保され、そこに segment header が置かれる (詳細: [file segment (inode) - 利用者ごとの segment 構成](../fsp/fseg.md#利用者ごとの-segment-構成))
- ヘッダーページの構成は以下

| オフセット | バイト数 | 説明 |
| --- | --- | --- |
| 0 | 4 | テーブルメタデータの B+Tree のメタページの PageNumber |
| 4 | 4 | インデックスメタデータの B+Tree のメタページの PageNumber |
| 8 | 4 | インデックスキーカラムメタデータの B+Tree のメタページの PageNumber |
| 12 | 4 | カラムメタデータの B+Tree のメタページの PageNumber |
| 16 | 4 | 制約メタデータの B+Tree のメタページの PageNumber |
| 20 | 4 | ユーザーメタデータの B+Tree のメタページの PageNumber |
| 24 | 4 | 次に割り当てる FileId |
| 28 | 4 | 次に割り当てるインデックス ID (グローバルで一意、1 から開始。0 は無効値) |
| 32 | 4 | Undo ログファイル用の FileId |
| 36 | 4 | DDL Undo 専用領域コンテナの先頭ページの PageNumber (カタログ初期化時に確保され、 サーバライフタイム中ずっと有効) |
| 40 | 4 | 次に払い出すトランザクション ID (1 から開始、 0 は予約値) |
| 44 | 6 | カタログヘッダー segment の segment header (詳細: [file segment (inode) - segment header](../fsp/fseg.md#segment-header)) |

- カタログファイルを開くときのファイル種別と FileId の検証は、page 0 の FSP ヘッダーに置かれたマジックナンバーと FileId の照合で行う (詳細: [ファイル空間管理 - FSP ヘッダー](../fsp/fsp.md#fsp-ヘッダー))

- 通常 Undo は専用ファイル (`Undo ログファイル用の FileId` 配下) に書き出されるのに対し、[DDL Undo](../access/ddl.md#ddl-undo-の役割と専用領域) は通常 Undo と分離された専用領域に書き出される。ヘッダーは両者の参照ポイントを別の項目として保持する
- DDL Undo 専用領域コンテナはカタログ作成時に 1 度確保され、 以降サーバライフタイム中ずっと同じ先頭ページを指し続ける。 個々の DDL 完了時はコンテナの中身 (= エントリ列) のみを物理破棄し、 コンテナ自体は次の DDL でそのまま再利用する
- 「次に割り当てる FileId」「次に割り当てるインデックス ID」「次に払い出すトランザクション ID」は単調増加させたまま据え置き、DDL のロールバックでも巻き戻さない (ID 値を再利用しない方針)
- 「次に払い出すトランザクション ID」は、ユーザートランザクション開始時の採番位置を再起動後も保持するために、Redo ログとは独立してヘッダーに永続化する。永続化と復元の経路は [トランザクション - トランザクション ID 採番位置の永続化と復元](../access/transaction.md#トランザクション-id-採番位置の永続化と復元) を参照

## テーブルメタデータ

- B+Tree の[レコード](../btree/node.md#レコード)はヘッダー領域・キー領域・非キー領域の 3 領域で構成される
  - 参考: https://dev.mysql.com/doc/refman/8.0/ja/information-schema-innodb-tables-table.html
- テーブルメタデータでは、各領域を以下のような内容で使用する (意味付けている)

| 領域 | 内容 | 説明 |
| --- | --- | --- |
| ヘッダー | - | テーブルメタデータのレコードは削除されない想定なので、ヘッダーは使用しない |
| キー | テーブル名 | - |
| 非キー | テーブルの属性情報 (詳細は以下) | - |

- 非キー領域の内容は以下のとおり
  - プライマリインデックスの B+Tree メタページ ID
  - テーブルのカラム数

## インデックスメタデータ

- インデックスメタデータでは、各領域を以下のような内容で使用する
  - 参考: https://dev.mysql.com/doc/refman/8.0/ja/information-schema-innodb-indexes-table.html

| 領域 | 内容 | 説明 |
| --- | --- | --- |
| ヘッダー | - | インデックスメタデータのレコードは削除されない想定なので、ヘッダーは使用しない |
| キー | FileId + インデックス名 | インデックスが属するテーブルの FileId とインデックス名を組み合わせたもの |
| 非キー | インデックスの属性情報 (詳細は以下) | - |

- 非キー領域の内容は以下のとおり
  - インデックス ID (グローバルで一意)
  - インデックスの種類
    - 1: プライマリインデックス
    - 2: 一意なセカンダリインデックス
    - 3: 一意でないセカンダリインデックス
  - インデックスを構成するカラム数
  - インデックスの B+Tree メタページ ID

## インデックスキーカラムメタデータ

- インデックスを構成するカラム情報を管理する
- 1 つのインデックスは複数のカラムで構成される場合があるため、インデックスメタデータとは分けている
- インデックスメタデータに直接カラム情報を持たせると、インデックスの種類などの属性が各カラム行に冗長に繰り返される (部分関数従属になる)
  - 補足: インデックスメタデータのキーを `インデックス ID + カラム名` にすれば正規化違反は回避できるが、インデックス自体の属性 (種類など) を取得するためだけにカラム数分の行を走査する必要があるのでそれは微妙
- インデックスキーカラムメタデータでは、各領域を以下のような内容で使用する
  - 参考: https://dev.mysql.com/doc/refman/8.0/ja/information-schema-innodb-fields-table.html

| 領域 | 内容 | 説明 |
| --- | --- | --- |
| ヘッダー | - | インデックスキーカラムメタデータのレコードは削除されない想定なので、ヘッダーは使用しない |
| キー | インデックス ID + カラム名 | インデックスメタデータのインデックス ID と構成するカラム名 (複合インデックスの場合はいずれか 1 つ) を組み合わせたものをキーとすることで、構成するカラム情報を一意に識別できるようにしている |
| 非キー | インデックスを構成するキーの情報 (詳細は以下) | - |

- 非キー領域の内容は以下のとおり
  - インデックス上のカラム位置

## カラムメタデータ

- カラムメタデータでは、各領域を以下のような内容で使用する
  - 参考: https://dev.mysql.com/doc/refman/8.0/ja/information-schema-innodb-columns-table.html

| 領域 | 内容 | 説明 |
| --- | --- | --- |
| ヘッダー | - | カラムメタデータのレコードは削除されない想定なので、ヘッダーは使用しない |
| キー | FileId + カラム名 | カラムが属するテーブルの FileId とカラム名を組み合わせたものをキーとすることで、テーブル内でカラムを一意に識別できるようにしている |
| 非キー | カラムの順序位置などの情報 (詳細は以下) | - |

- 非キー領域の内容は以下のとおり
  - カラムの順序位置
- カラムメタデータには、すべてのテーブルのカラム情報が含まれる

## 制約メタデータ

- 制約メタデータは PRIMARY KEY、UNIQUE KEY、FOREIGN KEY などの制約情報をカラム単位で管理する
- キーに `FileId + カラム名 + 制約名` を含むため、複合キー制約の場合は同じ制約名で複数行が存在する
  - 補足: インデックスメタデータとインデックスキーカラムメタデータは分けているのに、なぜ制約メタデータは分けていないのかについて
    - 制約の検索は「あるカラムにどんな制約があるか」の確認を目的とするため、対象テーブルのカラムを起点に行われる (=`FileId + カラム名` で検索)
    - よって制約名だけから属性を引くユースケースがなく、分離しても検索効率の改善にならないため、インデックスキーカラムメタデータのような分離はしてない
- 制約メタデータは、各領域を以下のような内容で使用する
  - 参考: https://dev.mysql.com/doc/refman/8.0/ja/information-schema-key-column-usage-table.html

| 領域 | 内容 | 説明 |
| --- | --- | --- |
| ヘッダー | - | 制約メタデータのレコードは削除されない想定なので、ヘッダーは使用しない |
| キー | FileId + カラム名 + 制約名 | 制約が属するテーブルの FileId、カラム名、制約名を組み合わせたものをキーとする |
| 非キー | 参照先の情報 (詳細は以下) | - |

- 非キー領域の内容は以下のとおり
  - 制約によって参照されるテーブルの FileId
    - 主キーやユニークキーの場合は無効値になる
  - 制約によって参照されるカラム名
    - 主キーやユニークキーの場合は空文字になる (NULL 未サポートのため)
- 主キーの場合、制約名は `PRIMARY` になる
- 外部キーだけでなく、カラムが主キーの場合、ユニークキーの場合なども制約として管理している

## ユーザーメタデータ

- ユーザーアカウントの認証情報を管理する

| 領域 | 内容 | 説明 |
| --- | --- | --- |
| ヘッダー | - | 使用しない |
| キー | ユーザー名 | ユーザーを一意に識別する |
| 非キー | ホスト名、認証文字列 (詳細は以下) | - |

- 非キー領域の内容は以下のとおり
  - ホスト名 (接続を許可するホスト)
  - 認証文字列 (`SHA256(SHA256(password))` の 32 バイト)
