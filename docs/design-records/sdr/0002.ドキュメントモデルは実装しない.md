# ドキュメントモデルは実装しない

## Motivation

X Plugin の主要な機能の 1 つに「ドキュメントモデル」がある。MySQL を MongoDB のようなドキュメントストアとして使うための機能で、SQL を書かずに JSON ドキュメントを出し入れできる。X Protocol を実装すると決めた以上、この機能をどこまで持つかを決める必要があった

## Decisions

- ドキュメントモデル (コレクション、CRUD メッセージ、コレクション系の管理コマンド、それらが前提にする JSON 型) は実装しない
- 対応するメッセージを受け取ったときは、未対応のメッセージとしてエラーを返す
  - MySQL と同じく、認証前なら致命的エラーとして接続を閉じ、認証後なら通常のエラーを返してセッションを続ける
- 仕様書では「X Plugin の機能の 1 つ」という位置づけの説明にとどめ、詳細は書かない

## Context

ドキュメントモデルの実体は、プロトコルの上にある変換層である。クライアントが送る CRUD メッセージ (`Find` / `Insert` / `Update` / `Delete`) を、X Plugin が「JSON カラムを 1 つ持つ普通のテーブル」に対する SQL に組み立て直して実行している。JSON 型と JSON 関数は MySQL サーバーが元々持つ機能で、X Plugin が足したものではない

この構造から、次のことが言える

- プロトコルの主要な部分 (フレーム、capability、認証、シーケンス、SQL の実行と結果の返送、Notice、セッションのリセット) は、ドキュメントモデルがなくても成り立つ
- 境界が `.proto` ファイルの単位で切れる
  - `mysqlx_crud.proto` と `mysqlx_expr.proto` を丸ごと省け、SQL 実行 (`StmtExecute`) の引数は汎用の値型なので式のツリーに依存しない
- RDB の内部構造を理解する目的には、ドキュメントモデルは独立した付加機能で、省いても学びは欠けない
