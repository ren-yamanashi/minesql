# 名前解決の規則は MySQL に合わせ、識別子は大文字小文字を区別しない

## Motivation

プリペアの名前解決で、書かれた名前をどの範囲でどの順に探し、どんなときにエラーにするかを決める必要があった。MySQL の規則はほぼそのまま使えるが、識別子の大文字小文字の扱いだけは OS 依存 (`lower_case_table_names`) で、MineSQL として 1 つに固定する必要があった

## Decisions

- テーブルの探し方
  - 修飾のないテーブル名はデフォルトスキーマで探し、デフォルトスキーマがなければエラー
  - `スキーマ.テーブル` はデフォルトスキーマによらずそのスキーマで探す
  - テーブルに別名を付けたら、そのステートメントの中では別名でだけ参照できる (元のテーブル名では参照できない)
  - 同じ FROM に同じ名前 (別名があれば別名、なければテーブル名) が 2 回現れたらエラー
- カラムの探し方
  - 修飾のないカラム名は FROM の全テーブルから探し、複数のテーブルにあればあいまいエラー、どこにもなければ未知のカラムのエラー
  - `テーブル.カラム`、`別名.カラム`、`スキーマ.テーブル.カラム` はそのテーブルからだけ探す
  - `*` と `テーブル.*` は FROM の順に、テーブルの定義の順で展開する
- ORDER BY の項目
  - 位置番号 (1 始まり) は select list のその位置の項目を指し、範囲外はエラー
  - 名前は select list (カラムの別名を含む) を先に探し、見つからなければ FROM のテーブルから探す
- 大文字小文字
  - スキーマ名、テーブル名、カラム名、テーブルの別名、カラムの別名のいずれも大文字小文字を区別しない
  - 定義に書かれた綴りをそのまま保存し、照合のときだけ大文字小文字の違いを無視する
  - 無視するのは大文字小文字の違いだけで、アクセントなど他の違いは区別する
- 名前解決の文脈 (そのクエリブロックで見えているテーブルの一覧) は、サブクエリがなくても外側の文脈を辿れる形で持つ

## Context

### MySQL に合わせる理由

名前解決の規則は、結果とエラーになる入力を決める。デフォルトスキーマの補完、別名、重複とあいまいさのエラー、`*` の展開順、ORDER BY の探索順を MySQL のとおりにし、MySQL 向けに書いた文が同じ意味で動くようにする。ORDER BY の位置番号は書き方としては勧められないが、実装は select list の位置を引くだけなので、外す理由がない

MySQL では、FROM の名前の重複の検査は文脈化 (parse tree から AST を作る段階) で行われる。MineSQL は文脈化を持たない ([SDR-0008](./0008.パーサーの出力は未解決のクエリブロックと式で文脈化を持たない.md)) ので、この検査はプリペアの名前解決に移る

### 大文字小文字を区別しない理由

MySQL では、カラム名とカラムの別名は常に区別せず、スキーマ名・テーブル名・テーブルの別名は `lower_case_table_names` に従う (Unix 系の既定は区別し、macOS と Windows の既定は区別しない)。識別子の種類ごとに規則が違うのは、テーブルがファイルシステム上のファイルだった時代の名残で、MineSQL が写す理由はない。全ての識別子を 1 つの規則にするなら、カラム名と同じ「区別しない」にする。これは MySQL の設定 1 と 2 に相当する

綴りをそのまま保存するのは MySQL の設定 2 に相当する。定義した人の綴りがディクショナリとエラーメッセージに残る

### MySQL との差

- MySQL の識別子の照合は大文字小文字だけでなくアクセントの違いも同一視する (`é` と `E` を同じとみなす) が、MineSQL は大文字小文字の違いだけを無視する
- Unix 系の既定 (`lower_case_table_names=0`) の MySQL では区別されるテーブル名が、MineSQL では区別されない

### 後から広げるとき何が変わるか

- サブクエリ: 名前解決の文脈を入れ子にし、内側で見つからない名前を外側で探す (文脈を外側へ辿れる形にしてあるので、探索の追加で済む)
- ビュー: ビューのカラムを定義の式に置き換える段階が要る
