# パーサーの出力は未解決のクエリブロックと式で、文脈化を持たない

## Motivation

MySQL のパーサーは、文字列を「文の形だけを写した木 (parse tree)」に変えたあと、それを辿って「クエリブロックと式」という意味の構造 (`Query_block` / `Item`) を組み立てる。クエリブロックと式を組み立てる段階を文脈化 (contextualize) と呼ぶ。MineSQL のパーサーがどこまでを担い、何を出力するかを決める必要があった

## Decisions

- パーサーの責務は「ステートメントの文字列 → AST」まで
  - 名前解決、型決定、データディクショナリの参照、クエリの変換は、プリペア以降の責務
- AST は、MySQL の `Query_block` / `Item` に相当する構造を未解決の状態で作ったもの
  - 句の単位 (SELECT なら select list、FROM、WHERE、ORDER BY、LIMIT) で構成する
  - 同義語 (`<>` と `!=`、`JOIN` と `INNER JOIN` など) はパーサーが同じノードにする
- プリペアは同じノードに解決結果 (カラムへの束縛、型) を書き込み、オプティマイザとエグゼキュータも同じ構造を使う
  - パーサーは解決結果の欄に一切書かず、解決済みかどうかは明示的な印で表す
  - オプティマイザとエグゼキュータは解決済みのノードだけを受け取る
- 形だけの木 (parse tree) と、それを意味の構造に変換する段階 (文脈化) は持たない

## Context

### MySQL に 2 本の木がある理由

MySQL の 2 本の木は、2 つの順序の衝突を解くために生まれた

- 構文解析器 (Bison) は「内側から外側へ」進む
  - カラム名を見つけ、式にまとめ、select list にし、最後に SELECT 全体を 1 つにまとめる
- 一方、MySQL の意味の構造は、生まれる時点で周囲を知っている必要があった
  - 式は自分がどのクエリブロックに属するかを、入れ子のクエリは外側のクエリを、一部の式は文中のどの位置にあるかを知って生まれる
  - これは「外側から内側へ」しか作れない

旧設計 (5.6 まで) は、この衝突を「SELECT を読んだ時点でクエリブロックを先に作り、見つかった部品を押し込む」という方法で無理に解いていた。その結果、解析器は常に「今どこにいるか」という状態を持ち、規則の途中に処理が挟まり、文法には 160 個近い衝突があった。5.7 の作り直し ([WL#6707](https://dev.mysql.com/worklog/task/?id=6707)) は、内側から外側へ素直に作れる形だけの木を前に置き、外側から内側へ辿る文脈化で意味の構造を作るようにした。意味の構造そのものは書き直せなかったので、2 本の木が残った

### MineSQL に 2 本目が要らない理由

parse tree が必要になるのは、意味の構造が生まれる時点で周囲を必要とするときだけである。MineSQL にはその必要がない

- サブクエリがないので 1 文に 1 クエリブロックで、入れ子の関係がない
- デフォルトスキーマの補完や文字集合の付与のような、セッションの状態に依存する作り分けがない
- 位置によって式の作り方が変わる句 (HAVING) がない

したがって「部品が揃ってから親を作る」という順序で、クエリブロックと式を最初から組み立てられる。文法規則の末尾のアクションで作れるので、組み替えの段階は要らない。パーサーがデータディクショナリやセッションを読まないという性質も保たれる

### 1 本の木にした理由

AST とプリペア後の構造を別に持つ案 (a) と、同じノードに解決結果を書き込む案 (b) を比べた

- (a) は構文と意味が別の型になり、同じ文を解き直す機能 (プリペアドステートメント、ビュー) に有利
- (b) は MySQL の下流 (プリペア・オプティマイザ・エグゼキュータが同じ `Query_block` / `Item` を使い続け、`fix_fields` で式が自分を解決する) と同じ形

決め手は「アーキテクチャと概念は MySQL に忠実」という軸である。プリペア以降が使う構造こそ、読者が MySQL のソースと見比べる部分だからである。(a) の利点は対象外の機能でしか現れない。(b) を採り、構文と意味を同居させる代償は「解決済みかどうかの印」と「パーサーは解決結果に書かない」という 2 つの約束で抑える

### 拡張性

サブクエリや HAVING を後から入れる場合も、「ノードは周囲を知らずに作れる」「周囲に依存する判断はプリペアで行う」の 2 つを守れば、文法とプリペアの追加で済む。MySQL の parse tree は、この約束を守れない構造を残したまま解析器だけを直すために必要になったもので、拡張性のために必要なものではない
