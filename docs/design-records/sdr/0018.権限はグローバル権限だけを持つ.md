# 権限はグローバル権限だけを持つ

## Motivation

アカウント管理ステートメントを対象に含める ([SDR-0017](./0017.アカウント管理ステートメントを対象に含める.md)) と、「誰がアカウント管理ステートメントを実行できるか」「誰が他の接続を kill できるか」に答えが要る。認証の方式 ([SDR-0015](./0015.認証の方式.md)) では権限を対象外にし、ACL キャッシュを「権限を入れるときの拡張点」としていた。権限をどの粒度まで持つかを決める必要があった

## Decisions

- グローバル権限 (`GRANT ... ON *.*`) だけを持ち、スキーマ単位・テーブル単位・カラム単位の権限、ロール、動的権限は持たない
- 権限は MineSQL のステートメントに対応する 9 つ: `SELECT` / `INSERT` / `UPDATE` / `DELETE` / `CREATE` / `DROP` / `ALTER` / `CREATE USER` / `GRANT OPTION`
  - `ALL [PRIVILEGES]` は `GRANT OPTION` を除く 8 つの略記 (MySQL と同じ)
  - `USAGE` (権限なしの明示) は採らない
- 保存先は `minesql.user` の行 (MySQL の `mysql.user` の `*_priv` カラムに相当) で、ACL キャッシュは引き続き持たない
- ステートメントは `GRANT priv_list ON *.* TO user [WITH GRANT OPTION]` と `REVOKE priv_list ON *.* FROM user`
  - `ON db.*` / `ON db.tbl`、カラムリスト、ロール、`PROXY`、`REVOKE ALL PRIVILEGES, GRANT OPTION FROM` は採らない
- 検査の時期と場所
  - 認証の成功時に、照合で読んだ `minesql.user` の行のグローバル権限を実行ユーザーに設定する
  - 各ステートメントはプリペアの入口 (名前解決の前) で、実行ユーザーのグローバル権限に必要な権限が含まれるかを検査する
    - 名前解決の後の 2 段階目の検査は持たない
  - `GRANT` / `REVOKE` の効果は次の接続からで、既存のセッションの実行ユーザーは変わらない (MySQL のグローバル権限と同じ)
- ステートメントごとに必要な権限
  - `SELECT` / `INSERT` / `UPDATE` / `DELETE`: 同名の権限
  - `CREATE TABLE` / `CREATE SCHEMA`: `CREATE`
  - `DROP TABLE` / `DROP SCHEMA`: `DROP`
  - `ALTER TABLE`: `ALTER`、`CREATE`、`INSERT` (MySQL と同じ)
  - `USE`: `SELECT` / `INSERT` / `UPDATE` / `DELETE` / `CREATE` / `DROP` / `ALTER` のいずれか (MySQL の「そのスキーマに対する何らかの操作権限」に相当)
  - `CREATE USER` / `ALTER USER` / `DROP USER`: `CREATE USER`
    - ただし実行ユーザー自身のパスワード変更 (`ALTER USER` で自分自身) は権限不要
  - `GRANT` / `REVOKE`: 与える (取り消す) 権限をすべて持ち、かつ `GRANT OPTION` を持つこと
  - トランザクション制御 (`BEGIN` / `START TRANSACTION` / `COMMIT` / `ROLLBACK`): 不要
- `KILL` と管理コマンド `kill_client` / `list_clients` は、同じアカウントの接続だけを対象にする (`SUPER` に相当する権限は持たない)
- 初期アカウントには bootstrap で `GRANT ALL PRIVILEGES ON *.* TO user WITH GRANT OPTION` を実行する

## Context

### MySQL の権限の形

- 保存先は 4 段階ある
  - グローバル権限は `mysql.user` の行 (31 個の `*_priv` カラム)、スキーマ単位は `mysql.db`、テーブル単位は `mysql.tables_priv`、カラム単位は `mysql.columns_priv`
  - ほかに動的権限とロールがある
- 起動時にこれらをメモリ上の ACL キャッシュに読み込み、ログイン時に user@host をパターン照合して、グローバル権限とスキーマ権限を実行ユーザーへ写す
  - X Plugin の実行ユーザーの切り替えも同じ処理を通る
- 検査は 2 段階ある
  - 名前解決の前に、ステートメントの種類ごとに粗く検査する (グローバル権限で足りるか → スキーマ権限 → テーブル権限へ)
  - 名前解決の後に、テーブルとカラムの単位で検査する
  - DDL とアカウント管理ステートメントも同じ枠で、`CREATE USER` 系は `CREATE USER` 権限、`GRANT` は「与える権限を自分が持ち、かつ `GRANT OPTION`」を要求し、自分のパスワード変更だけは権限を要求しない
- `GRANT ... ON *.*` は `mysql.user` の同じ行を更新し、`ON db.*` は `mysql.db` に行を書く
  - 初期化時の `root@localhost` は `GRANT ALL PRIVILEGES ON *.* ... WITH GRANT OPTION` で作られる
- `KILL` は `SUPER` か `CONNECTION_ADMIN` を持つか、同じユーザー名の接続に限る (ホストは比べない)
  - X Plugin の `list_clients` も、`SUPER` を持たなければ同じユーザー名の接続だけを返す

### 比べた案

- 権限なし: 認証で決めた「誰か」を何にも使わず、アカウント管理ステートメントを入れると誰でもアカウントを操作できる状態になる
  - MySQL にも権限テーブルを読まずに動く形 (`--skip-grant-tables`) はあるが、それは認証も行わない運用モードで、認証だけを持つ形とは違う
- グローバル権限のみ (採用): グローバル権限の経路 (行に権限がある → ログイン時に実行ユーザーへ写す → プリペアの入口で検査する → `GRANT` が同じ行を更新する) を欠けなく写せる
  - MineSQL は認証で `minesql.user` の行を SQL で読むので、同じ行の権限を実行ユーザーに設定でき、ACL キャッシュが要らない
- スキーマ・テーブル単位まで: 検査を名前解決の前後 2 段階に分ける構造と、スキーマ名のワイルドカード照合、テーブル単位の権限を持つメモリ構造が要る
  - 2 段階の検査は MySQL の権限検査の特徴だが、その構造はプリペアの設計そのものなので、粒度を上げるなら 2 段階目の検査点を足すときに改めて判断する

### 細部の理由

- 9 つに絞る: 文法に含めたステートメントが要求する権限だけを持つ
  - `REFERENCES` や `INDEX` のように対応するステートメントがない権限は、与えても検査されない
- `ALL` が `GRANT OPTION` を含まない: MySQL の `GRANT ALL ON *.*` は `GRANT OPTION` を除いたグローバル権限を与え、`WITH GRANT OPTION` で別に与えるので、同じにする
- 効果が次の接続から: グローバル権限はログイン時に実行ユーザーへ写され、検査はその写しに対して行う
  - MySQL と同じ振る舞いで、`GRANT` のたびに全セッションを更新する仕組みを持たずに済む
- `SUPER` を持たない: `SUPER` は多くの管理操作をまとめた権限で、MineSQL でそれが要る操作は kill と接続の一覧しかない
  - 「同じアカウントの接続のみ」に限れば、権限を 1 つ増やさずに済む
- 自分のパスワード変更に権限を要求しない: MySQL と同じ
  - 要求すると、`CREATE USER` 権限のないアカウントが自分のパスワードを変えられなくなる

### 後から広げるとき

- スキーマ・テーブル単位: `mysql.db` / `mysql.tables_priv` を足し、名前解決の後の検査点を 008_prepare/ に足す
  - プリペアの入口の検査はそのまま残る
- `SUPER` 相当: kill と一覧の条件に「この権限を持つなら全接続」を 1 つ足す
- user@host のパターン照合: ホストを `%` 以外にするとき、[SDR-0015](./0015.認証の方式.md) の言う ACL キャッシュの導入とあわせて行う
