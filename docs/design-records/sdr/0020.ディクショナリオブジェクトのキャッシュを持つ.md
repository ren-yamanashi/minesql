# ディクショナリオブジェクトのキャッシュを持つ

## Motivation

定義をディクショナリテーブルに置く ([SDR-0019](./0019.ディクショナリテーブルはストレージエンジンのテーブルとして持つ.md)) と、名前解決のたびにテーブルを読むか、一度読んだ定義をメモリに保持するかを決める必要があった。MySQL は共有のオブジェクトキャッシュと、接続ごとのクライアントの 2 層で保持している

## Decisions

- 読み込んだ定義 (ディクショナリオブジェクト) を保持する、全接続で共有するオブジェクトキャッシュを持つ
  - 定義の種類 (スキーマ、テーブル) ごとに区画を分け、名前と id で引ける
  - キャッシュにないときだけディクショナリテーブルを読み、同じ定義を同時に要求されても読み込みは 1 回にする
  - 使用中のオブジェクトの数を数え、未使用になったものを容量の範囲で保持し、容量を超えたら最も長く使われていないものから捨てる
  - 容量は設定値で持つ
- 定義の取得は内部セッションごとのディクショナリクライアントを通してだけ行う
  - クライアントは取得したオブジェクトを手元に登録し、同じ処理の中で 2 度目以降は手元から返す
  - 処理の終わりに登録したオブジェクトを解放する
- 定義の変更と削除は、キャッシュの中の古いオブジェクトを外し、次の取得でディクショナリテーブルから読み直させる
- 変更の競合を防ぐメタデータロックは持たず、同時に実行される DDL は対象外にする (issue #120 の「並行 DDL」)

## Context

### 比べた案

- キャッシュを持つ (採用): MySQL 8.0 の形
  - 名前解決のたびにディクショナリテーブルを読まずに済む
  - 本で「キャッシュの整合性」を示す題材になる
    - 定義が変わったときに古いオブジェクトをどう外すか、使用中のオブジェクトをどう守るか、という問題はキャッシュ一般に共通する
- 毎回ディクショナリテーブルを読む: 実装は最も小さい
  - 定義の参照は SQL の実行の中で最も頻繁な処理の 1 つなので、ステートメントごとにテーブルの行から組み立て直す費用が大きい
  - キャッシュの整合性という題材が本から消える

### MySQL との違い

MySQL には、ディクショナリオブジェクトのキャッシュのほかに、テーブルを開くための構造 (TABLE_SHARE) のキャッシュ (table definition cache) が並存している。歴史的な二重構造で、MineSQL はディクショナリオブジェクトのキャッシュだけを持つ

### 後から広げるとき

並行 DDL を入れるときは、定義ごとのメタデータロックを足し、変更は排他ロックの下でだけ行う。キャッシュの形は変わらない
