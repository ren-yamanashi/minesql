# 実装対象は X Protocol に従うサーバー

## Motivation

MySQL には、クライアントとサーバーが会話するための通信規約が 2 つある。古くからある classic protocol と、5.7.12 で加わった X Protocol である。MineSQL はどちらに従うサーバーにするかを決める必要があった

- 2 つは並存していて、サーバーの中でも別々の入口 (ポート 3306 と 33060) と別々の受付処理を持つ
- どちらを選ぶかで、コネクションハンドラーの形、メッセージの読み書き、認証の進め方がすべて変わる

## Decisions

- MineSQL は X Protocol に従うサーバーとして作る
  - MySQL でいえば X Plugin に相当する層 (接続の受付、プロトコル処理、セッション、ステートメントの実行の依頼) を実装する
- classic protocol は実装しない
  - 仕様書では、X Protocol の設計を理解するための対比として触れるにとどめる

## Context

classic protocol では、メッセージの意味が直前に何を送ったかで決まる。1 つのコマンドの応答を受け取ってから次を送る前提で作られている。capability (接続で何ができるか) はビットフラグで運ばれ、32 ビットの枠はほぼ使い切られている。長い歴史の中で拡張が積み重なった結果で、仕組みを一から追うには前提知識が多い

X Protocol は、これらの制約をなくすように設計し直されている

- メッセージの構造を `.proto` ファイルで定義し、フレームの先頭に種別を持たせるので、どのメッセージも同じ手順で読める
- リクエストとレスポンスの対応が「シーケンス」という単位で規定され、応答を待たずに次を送れる
- capability は名前つきの値、サーバーからの付随情報は Notice という独立したメッセージで運ぶ

学習用の小さい MySQL を作る目的には X Protocol の方が合う。設計の意図が仕様に書かれていて実装の根拠を追いやすく、`.proto` から各言語のコードを生成でき、公式のクライアント (MySQL Shell や各言語の Connector) でそのまま試せる

X Protocol の接続は X Plugin が独自に受け付け、サーバー本体の classic 用コネクションハンドラーを通らない。したがって classic を持たなくても失うのは classic 用の受付処理だけで、内部セッション以降には影響しない

## Result

- 仕様書は X Protocol / X Plugin を正として書く ([001_protocol/](../../specification/001_protocol/README.md)、[002_connection/](../../specification/002_connection/README.md)、[003_dispatcher/](../../specification/003_dispatcher/README.md))
- classic protocol との対比は [001_protocol/x_protocol.md](../../specification/001_protocol/x_protocol.md) の「classic protocol との違い」にまとめる
