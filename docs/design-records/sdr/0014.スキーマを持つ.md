# スキーマを持つ

## Motivation

当初、MineSQL はスキーマ (データベース) を持たない前提で、パーサーからも `スキーマ名.テーブル名` の修飾を外していた。認証の方式を決める過程 ([SDR-0015](./0015.認証の方式.md)) で、アカウント情報を MySQL と同じくシステムテーブルに置いて SQL で検索するには、システムテーブルと利用者のテーブルを分ける名前空間が要ると分かった。そこで前提を見直した

## Decisions

- スキーマを持つ
  - システムテーブル (`user`) を置くスキーマの名前は minesql にし (MySQL の mysql スキーマに相当)、利用者のテーブルは利用者のスキーマに置く
  - `user` テーブルは普通のテーブルとして扱い、グローバル権限を持つアカウントは直接読み書きできる (MySQL の `mysql.user` と同じ)
  - デフォルトスキーマは接続時 (`AuthenticateStart.schema`) に決まり、修飾のないテーブル名はそこで解決する
- `CREATE SCHEMA` / `DROP SCHEMA` (`DATABASE` と同義) と `USE` (デフォルトスキーマの切り替え) も対象に含める
- 層ごとの分担
  - パーサー: `スキーマ名.テーブル名` と `スキーマ名.テーブル名.カラム名` の修飾を受理し、`CREATE SCHEMA` / `DROP SCHEMA` / `USE` の規則を写す
  - プリペア: 修飾のないテーブル名をデフォルトスキーマで解決する
  - データディクショナリ: スキーマを実体として持ち、テーブルはスキーマに属する
  - コネクションハンドラーと内部セッション: 接続時にデフォルトスキーマを内部セッションに設定し、`USE` で切り替える

## Context

スキーマを入れない案では、システムテーブルを「内部セッションだけが見える予約名のテーブル」として扱う。これでは `スキーマ名.user` という置き方も、システムテーブルが普通のテーブルであるという構造も再現できない。本でスキーマとシステムテーブルの関係を示すには、最小のスキーマ機能を入れる方が合う

パーサー側では、以前「スキーマがない」を理由に外していた修飾を採用に戻すだけで済む。外した規則を理由つきで記録しておいた ([SDR-0011](./0011.文法に含める構文の範囲.md)) ことが、ここで役に立った

スキーマの名前は MySQL の mysql を写さず minesql にする。中身が MySQL の mysql スキーマとは異なる (テーブルは `user` とディクショナリテーブルだけで、`user` のカラムも一部しかない) ため、同じ名前にすると MySQL 向けのステートメントやツールがそのまま使えるように見えてしまう。設定変数の名前と同じく、MySQL の名前そのものは写さない
