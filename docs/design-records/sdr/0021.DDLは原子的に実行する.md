# DDL は原子的に実行する

## Motivation

`CREATE TABLE` や `DROP TABLE` は、ディクショナリテーブルの行の変更と、ストレージエンジンでのテーブルの作成・削除という 2 つの変更を伴う。途中でサーバーが止まったとき、行の変更とテーブルの作成・削除のどちらか一方だけが残る状態を許すかどうかを決める必要があった。issue #120 の「明示的な DDL の ROLLBACK 文はなし」との関係も整理する必要があった

## Decisions

- 1 つの DDL が行うディクショナリテーブルの変更とストレージエンジンの操作は、1 つのトランザクションとしてまとめて確定する
  - サーバーが途中で止まっても、両方が確定しているか、両方が残っていないかのどちらかになる
- DDL はトランザクショナルではない
  - DDL の実行前に、そのセッションで進行中のトランザクションを暗黙にコミットする
  - DDL の完了後にも暗黙にコミットし、DDL を `ROLLBACK` で取り消すことはできない
  - この振る舞いは `CREATE TABLE` / `DROP TABLE` / `CREATE SCHEMA` / `DROP SCHEMA` と、アカウント管理ステートメント、`GRANT` / `REVOKE` に共通
- ストレージエンジン側の操作 (表領域やページの確保と解放) のうちトランザクションで戻せないものは、DDL ログで扱う (MySQL の方式に倣う)
  - 操作の前に DDL ログへ記録し、コミット後に不要になったものを片付ける
  - 失敗やクラッシュの後は記録を再生して元に戻す

## Context

### 原子的な DDL とトランザクショナルな DDL は別

「原子的」は 1 つの DDL の内部の話で、「トランザクショナル」は利用者のトランザクションに DDL を含められるかという話である。MySQL 8.0 は原子的な DDL だけを実装していて、マニュアルも「Atomic DDL is not transactional DDL」と断っている。MineSQL も同じ範囲にする。issue #120 の「明示的な DDL の ROLLBACK 文はなし」はトランザクショナルな DDL の話で、この判断と矛盾しない

### 原子的にする理由

MySQL 5.7 までは定義がファイルと非トランザクショナルなテーブルに散らばっていたため、DDL の途中でサーバーが止まると、ファイルだけが残る、ディクショナリだけが更新される、といった食い違いが起きた。8.0 でディクショナリテーブルを InnoDB のテーブルにしたことで、定義の変更をトランザクションで確定できるようになり、その上で DDL 全体を原子的にできた。ディクショナリテーブルをストレージエンジンのテーブルとして持つ ([SDR-0019](./0019.ディクショナリテーブルはストレージエンジンのテーブルとして持つ.md)) 以上、行の側の原子性は自然に得られる。残るのはストレージエンジン側のファイルやページの操作で、これを DDL ログで扱う

### MySQL の手順

MySQL は 1 つの DDL を 4 段階で行う

- 準備: 必要なファイルや B ツリーを作り、取り消しに要る記録を DDL ログに書く
- 実行: インデックスの構築など
- コミット: ディクショナリテーブルの変更を確定する
- 後始末: DDL ログの記録を再生して、不要になったものを片付ける

DDL ログはそれ自体がディクショナリ表領域の中の隠しテーブルで、その変更はすぐに永続化される。クラッシュ後の復旧では、通常の redo と undo のあとに DDL ログを再生する

### 後から広げるとき

`ALTER TABLE` や `TRUNCATE TABLE` を入れるときも、同じ 4 段階で実行する。DDL ログに記録する操作の種類が増えるだけで、枠組みは変わらない
