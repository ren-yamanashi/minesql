# ディクショナリテーブルはストレージエンジンのテーブルとして持つ

## Motivation

スキーマを持ち、minesql スキーマにシステムテーブルを置くと決めた ([SDR-0014](./0014.スキーマを持つ.md)) 時点で、テーブルやカラムの定義そのもの (データディクショナリ) をどこに永続化するかは未決だった。定義をどこに置くかは、DDL の原子性、起動の手順、ストレージエンジンとの境界の全部を左右するため、データディクショナリの仕様を書く前に決める必要があった

## Decisions

- 定義 (スキーマ、テーブル、カラム、インデックス、インデックスのカラム) は、ディクショナリテーブルと呼ぶテーブルの行として持つ
  - ディクショナリテーブルは minesql スキーマに置き、ストレージエンジンの普通のテーブルとして作る
  - 利用者からは見えないテーブルにし、利用者のステートメントからの直接の参照と変更は拒否する
- 定義の変更は、ディクショナリテーブルの行の変更として、トランザクションの中で行う
- ディクショナリテーブルの定義そのものはコードに持つ (ハードコード)
  - 初回の起動では、コードの定義からディクショナリテーブルをストレージエンジンに作り、できたテーブルに自分たち (ディクショナリテーブルと minesql スキーマ) の定義を書き込む
  - 2 回目以降の起動では、コードの定義からテーブルを開き、テーブルの中の定義と比べて同期する
- システムテーブル (`minesql.user`) はディクショナリテーブルではなく、同じスキーマに置く普通のテーブルとして扱う

## Context

### 比べた案

- ディクショナリテーブルをストレージエンジンのテーブルとして持つ (採用): MySQL 8.0 の形
  - 定義の変更が普通の行の変更になるので、ストレージエンジンのトランザクションがそのまま定義の原子性になる ([SDR-0021](./0021.DDLは原子的に実行する.md))
  - 「定義もテーブルである」ことと、そのテーブルを作るために定義なしで動く起動の手順 (bootstrap) を、本で見せられる
- 定義を別のファイルに持つ: MySQL 5.7 までの .frm ファイルに相当する形
  - ファイルの書き込みはトランザクションに含められないため、DDL の途中でサーバーが止まると定義とデータが食い違う
    - MySQL がこの形をやめた理由そのもの
  - 実装は小さいが、本で示したい仕組み (原子的な DDL、bootstrap) を示せない

### 順序への影響

ディクショナリテーブルを読み書きするには、その前にストレージエンジンが動いている必要がある。本の順序では、ストレージエンジンのテーブルの読み書きができた後にデータディクショナリを入れる。ディクショナリテーブルの読み書きは SQL の経路 (パーサー → プリペア → オプティマイザ → エグゼキュータ) を通さず、ストレージエンジンのテーブルの操作を直接使う。MySQL も同じで、ディクショナリテーブルの行の読み書きは SQL を経由せず、ストレージエンジンの API を直接呼ぶ

### 後から広げるとき

定義の種類 (外部キー、ビュー、表領域など) を増やすときは、ディクショナリテーブルと、それに対応するメモリ上のオブジェクトを 1 種類ずつ足す。テーブルの形と起動の手順は変わらない
