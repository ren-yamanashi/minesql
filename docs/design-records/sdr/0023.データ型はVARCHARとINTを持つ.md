# データ型は VARCHAR と INT を持つ

## Motivation

issue #120 の「やらないこと」には当初「VARCHAR 以外のデータ型」が挙がっていて、[SDR-0011](./0011.文法に含める構文の範囲.md) もそれに従って VARCHAR 以外の型を文法から外していた。一方で、式の文法には数値リテラルと算術演算を採用している。数値が式の中にはあるのに、カラムの型としては持てない状態のままでよいかを、プリペア (型決定) の仕様に入る前に決める必要があった

## Decisions

- カラムの型は `VARCHAR` と `INT` の 2 つにする
  - `INT` は符号付き 4 バイトの整数
- `INT` に付随する次の構文は採らない
  - 大きさの違う整数型 (`TINYINT` / `SMALLINT` / `MEDIUMINT` / `BIGINT`)
  - `UNSIGNED`、`ZEROFILL` (8.4 で非推奨)、表示幅 `INT(11)` (非推奨)
  - `SIGNED` (MySQL 自身が読み飛ばす語)
- NULL を対象外にしている (issue #120) ため、どちらの型のカラムも暗黙に NOT NULL
- `AUTO_INCREMENT` は引き続き対象外
- `INT` と `VARCHAR` が混ざる比較 (`varchar_col = 1`、`int_col = '1'`) と算術の型の規則は別に決める ([SDR-0024](./0024.型の規則はMySQLに合わせ小数は浮動小数点で持つ.md))

## Context

### INT を含める理由

式の文法は数値リテラル (整数、小数、指数表記) と算術・ビット演算を採用している。VARCHAR しか持たないと、`WHERE id = 1` のような比較は MySQL の規則では「文字列と数値の比較は浮動小数点で行い、文字列カラムのインデックスは使えない」ものになる。MineSQL がこの規則を写せば VARCHAR しかないのに浮動小数点比較を持つことになり、写さなければ `'1'` と書くことを強制する独自規則になる。どちらも不自然で、INT を持てば `id = 1` は同じ型どうしの比較として成立する

説明の面でも、型が 2 つあることで「型ごとに変わるもの」を示せる

- 格納形式: InnoDB は整数を big-endian・符号ビット反転で格納し、バイト比較で大小が決まるようにしている
  - 文字列は照合順序で比較する
- ワイヤ形式: X Protocol は整数を `SINT`、文字列を末尾に `0x00` を 1 バイト足した `BYTES` で送る
- レコード形式: 固定長カラムと可変長カラムの対比

### 採る形を最小にする理由

INT 1 つで上の説明は足りる。残りはいずれも仕組みの説明に要らない

- 大きさの違う整数型は、格納バイト数が違うだけ
- `UNSIGNED` は、符号ビットを反転するかどうかの分岐が増えるだけ
- `ZEROFILL` と表示幅は、非推奨の表示上の機能

### 後から広げるとき何が変わるか

- 大きさの違う整数型: 型の一覧とバイト数の対応が増えるだけで、比較と格納の規則は同じ
- `UNSIGNED`: 格納時に符号ビットを反転しない分岐と、比較の型の規則の場合分けが増える
- 小数・浮動小数点・日時: リテラルの種類は字句解析にあるが、格納形式と比較の規則を型ごとに足す必要がある

## Result

- [SDR-0011](./0011.文法に含める構文の範囲.md) の「含めないもの」を「VARCHAR と INT 以外の型」に変更
- issue #120 の「VARCHAR 以外のデータ型」を「VARCHAR と INT 以外のデータ型」に変更
