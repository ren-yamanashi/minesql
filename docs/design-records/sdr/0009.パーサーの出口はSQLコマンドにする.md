# パーサーの出口は SQL コマンドにする

## Motivation

パーサーが AST を作ったあと、それをどうプリペア以降の段階に渡すかを決める必要があった。MySQL は、パーサー工程の出口で文の種別に応じた「SQL コマンド」(`Sql_cmd`) を作り、呼び出し側はそれをプリペアしてから実行する

## Decisions

- パーサーの出口は、AST を持つステートメント種別ごとの SQL コマンドとする
  - SQL コマンドは MySQL の `Sql_cmd` に相当し、プリペアと実行の 2 つの操作 (`prepare` / `execute`) を持つ
- 内部セッションは「パースして SQL コマンドを受け取り、プリペアしてから実行する」だけで、文の種別で分岐する switch を持たない

## Context

MySQL の出口は 2 段になっている。構文解析器そのものは parse tree の根を返し、パーサー工程 (`parse_sql`) がそれを文脈化して SQL コマンドを作り、`LEX` に入れて返す。受け取る側の `mysql_execute_command` には、文の種別で分岐する大きな switch が残っている。ただし `Sql_cmd` のクラスコメントは「新しい文は `Sql_cmd` の派生で実装せよ」と書いており、switch は移行途中の名残である

MineSQL はこの新しい側の形だけを取る。種別から SQL コマンドへの対応は「どの文法規則が還元されたか」だけで決まり、文脈もデータディクショナリも読まないので、パーサーの文脈非依存は保たれる

反対意見として「パーサーの責務は文字列から AST までに限るべきだ」を検討した。種別の対応は構文だけで決まり、意味の判断が入らないので、越権にはならないと判断した。DDL やトランザクション制御のようにプリペアで解決するものがないステートメントは、MySQL と同じく、プリペアでは権限の検査だけをして何も解決しない SQL コマンドにすればよい
