# プリペアで行うことの範囲

## Motivation

パーサーの出口は SQL コマンドで ([SDR-0009](./0009.パーサーの出口はSQLコマンドにする.md))、SQL コマンドはプリペアと実行の 2 つの操作を持つ。名前解決と型決定をプリペアが行うこと ([SDR-0008](./0008.パーサーの出力は未解決のクエリブロックと式でコンテキスト化を持たない.md)) は決めてあった。決めていなかったのは、ステートメントの種別ごとにプリペアが何をするか、定義の取得とテーブルのロックをどちらの段階に置くか、クエリの変換をどこで行うかの 3 つで、プリペアの論理モデルを書く前に決める必要があった

## Decisions

- 種別ごとのプリペアの範囲
  - 全ての種別で、プリペアの入口で実行ユーザーのグローバル権限を検査する ([SDR-0018](./0018.権限はグローバル権限だけを持つ.md))
  - SELECT / INSERT / UPDATE / DELETE は、続けて対象のテーブルの定義をデータディクショナリから取り、名前解決と型決定を行い、解決済みの印を付ける
  - それ以外の種別 (CREATE / DROP TABLE、CREATE / DROP SCHEMA、USE、アカウント管理ステートメントと GRANT / REVOKE、トランザクション制御、KILL) は、プリペアでは権限だけを検査する
    - 定義の検証 (同名のテーブル、カラム名の重複、アカウントの有無など) はその実行時に行う
- 定義の取得とロックの境界
  - プリペアはデータディクショナリから定義を取るだけで、ストレージエンジンのテーブルを開かない
  - 実行時にストレージエンジンのテーブルを開き、トランザクションに登録し (ロック)、行を読み書きする
- クエリの変換
  - プリペアの最後に「結合の単純化」を行う: 内部結合の ON 条件を WHERE に移し、FROM の入れ子 (`,` 区切りと `JOIN ... ON` の混在、括弧) を平坦なテーブルの並びと 1 つの条件にする
  - これ以外のクエリの変換はプリペアでは行わない
- プリペアの回数
  - ステートメントごとに毎回、解析し、プリペアし、実行する
    - プロトコルのプリペアドステートメントを持たないため ([SDR-0003](./0003.プロトコルのプリペアドステートメントとカーソルは実装しない.md))
  - したがって解決結果は AST に直接書き込んでよく、プリペアやオプティマイザが AST に加えた変更を後で戻す仕組みは持たない

## Context

### 種別ごとの範囲を MySQL に合わせる理由

MySQL では、SQL コマンドのプリペアは基底では何もしない。DML だけがこれを上書きし、権限の事前検査、テーブルを開くこと、名前解決と型決定を行う。CREATE TABLE のプリペアは権限の事前検査と `CREATE TABLE ... SELECT` の SELECT 部分だけで、テーブル定義の検証は実行時に行う。CREATE USER や GRANT は SQL コマンドですらなく、種別の分岐から直接実行される。MineSQL はプリペアドステートメントを持たないので、検証をどちらの段階に置いても観測できる差はない。そこで MySQL と同じ「DML だけがプリペアの本体を持つ」形にした

MySQL と違うのは権限の検査をどこで行うかである。MineSQL は全ての種別を SQL コマンドにし、その入口で検査する。MySQL では種別ごとに検査の場所が異なるが、検査の内容は同じである

### 定義の取得とロックの境界を MySQL に合わせる理由

MySQL はプリペアでテーブルを開く (定義の取得、テーブルオブジェクトの用意、メタデータロック)。SQL コマンドの実行処理は「未プリペアならプリペア → テーブルをロック → 本体の実行」の順に進む。MineSQL でも、定義の参照 (データディクショナリ) と行の読み書き (ストレージエンジン) の境界を、プリペアと実行の境界に一致させる。こうするとプリペアが失敗してもストレージ側の後始末が要らない。MineSQL はメタデータロックを持たない ([SDR-0020](./0020.ディクショナリオブジェクトのキャッシュを持つ.md))。後から並行 DDL を入れるときは、MySQL と同じく「定義を取る」ところにメタデータロックが付く

### 結合の単純化をプリペアの最後に置く理由

MySQL はプリペアの最後に恒久的なクエリの変換をまとめて行い、その 1 つが結合の単純化である。この変換は、外部結合を内部結合に変え、内部結合の ON 条件を WHERE に移し、不要な入れ子を除き、テーブル間の依存関係を計算する。MineSQL の文法は `,` 区切りの FROM と `JOIN ... ON` の両方を受理するので、平坦にする変換は MineSQL にも要る。内部結合だけなら ON と WHERE の意味は同じで、どこで移しても結果は変わらない。それでも MySQL と同じ位置に置けば、後から外部結合を入れるときに「外部結合の内部結合化」を同じ場所に足すだけで済む。プリペアドステートメントを後から入れる場合も、変換済みの AST をそのまま保持して実行を繰り返せるので、MySQL がこの位置にした理由がそのまま当てはまる (2026-09-30 に確認)。パーサーが最初から平坦な形で AST を作る案は、どの条件が ON に書かれたかという構文の情報を落とすため採らない ([SDR-0008](./0008.パーサーの出力は未解決のクエリブロックと式でコンテキスト化を持たない.md) の「構文を写した AST」の方針)

### 毎回プリペアすることの帰結

MySQL はプリペアドステートメントのためにプリペアを 1 回だけ行い、オプティマイザやエグゼキュータが加える変更を「一時的な変更」として記録して次の実行の前に戻す。MineSQL にはこの区別が要らない。[SDR-0008](./0008.パーサーの出力は未解決のクエリブロックと式でコンテキスト化を持たない.md) で決めた「解決結果を同じノードに書き込む」形は、この帰結と整合する

### 後から広げるとき何が変わるか

- プロトコルのプリペアドステートメント: プリペアの結果を保持して実行を繰り返すには、オプティマイザが AST に加える変更を実行のたびに戻す仕組みが要る
- 並行 DDL: メタデータロックを「定義を取る」ところに足す
- 外部結合: 結合の単純化に「外部結合の内部結合化」を足す
- サブクエリと派生表: プリペアの最後の変換に、サブクエリの変換と派生表の併合が加わる
