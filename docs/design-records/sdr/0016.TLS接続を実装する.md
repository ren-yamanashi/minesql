# TLS 接続を実装する

## Motivation

X Protocol では、接続を暗号化するかどうかをクライアントが capability `tls` で選ぶ。認証の `PLAIN` は安全な接続 (TLS または Unix ソケット) でしか使えないため、TLS を持たないと TCP 経由のクライアントは `PLAIN` を使えず、`SHA256_MEMORY` の前提となるキャッシュも Unix ソケット経由でしか埋められない。認証の方式 ([SDR-0015](./0015.認証の方式.md)) を決める過程で、TLS を実装対象に含めるかどうかが未決のまま残っていた

## Decisions

- TLS 接続を実装する
  - クライアントが `CapabilitiesSet` で `tls` を `true` に設定したら、`Ok` を返したあと同じ接続を TLS に切り替える
  - MySQL と同じく、`false` への設定と、すでに TLS になっている接続での再設定はエラーにする
  - TLS になった接続は Unix ソケットと同じく「安全な接続」として扱い、`PLAIN` を受け付け、`authentication.mechanisms` の一覧も安全な接続のものに切り替える
- サーバー証明書と秘密鍵は設定で与える (MySQL の `mysqlx_ssl_cert` / `mysqlx_ssl_key` に相当)
  - 証明書の自動生成と、クライアント証明書の検証は対象外
- アカウント単位の TLS 要件 (`require_secure_transport`、アカウントの `ssl_type`) の検査は、引き続き対象外 ([SDR-0015](./0015.認証の方式.md))

## Context

TLS の有無で変わるのは「どの経路が安全な接続とみなされるか」で、認証の仕組みは変わらない

- TLS がない場合、TCP からは `MYSQL41` (`caching_sha2_password` のアカウントには常に失敗) と `SHA256_MEMORY` (キャッシュが空なら失敗) しか試せず、ユーザーは先に Unix ソケットで `PLAIN` を通さなければならない
  - MySQL Shell などの公式クライアントを TCP からそのまま使うには TLS が要る
- capability `tls` は、実クライアントが接続直後に使うプロトコルの契約である
  - 「capability で合意してから、同じ接続の上で暗号化を始める」という切り替えは、X Protocol が capability を名前つきの値として交換する設計の効果を示す題材になる
- 加わる実装は、capability の処理、接続の切り替え、接続種別 (TCP / TLS / Unix ソケット) の判定で、いずれもコネクションハンドラーの中で済む
  - 認証側は「安全な接続かどうか」を判定するだけで変わらない

MySQL の X Plugin では、`Capability_tls` が `true` の設定だけを受け付け (TLS 未対応のサーバーや、すでに TLS の接続では失敗)、適用時に接続を TLS に切り替える (`handler_tls.cc:55-73`)。証明書と鍵は `mysqlx_ssl_*` の変数で与え、指定がなければサーバー本体の設定を引き継ぐ

### クライアント証明書の検証を対象外にする理由

TLS のハンドシェイクでは、サーバーが自分の証明書を示し、クライアントがそれを検証する (サーバー認証)。これに加えて、サーバーがクライアントにも証明書を要求し、信頼する認証局 (CA) で検証する形がある (クライアント証明書の検証、相互 TLS)。MySQL では `mysqlx_ssl_ca` / `mysqlx_ssl_capath` / `mysqlx_ssl_crl` で CA と失効リストを与えるとこの検証が働く。アカウント側の `REQUIRE X509` / `REQUIRE ISSUER` / `REQUIRE SUBJECT` (`mysql.user` の `ssl_type` / `x509_issuer` / `x509_subject`) と組み合わせると、証明書を持つクライアントだけにログインを許せる

MineSQL が TLS を持つ目的は、接続を安全な接続にして `PLAIN` を使えるようにし、通信を暗号化することである。これにはサーバー証明書だけで足りる。クライアント証明書の検証は、パスワードとは別の本人確認をトランスポート層で行う仕組みで、アカウントごとの TLS 要件の検査 ([SDR-0015](./0015.認証の方式.md) で対象外) と一体である。CA と失効リストの設定、クライアントへの証明書の配布と更新という運用が増える一方、本で示したい「capability で合意してから同じ接続を暗号化する」「安全な接続でだけ平文の認証を許す」という話には関わらない

後から入れる場合は、CA の設定を足し、TLS のハンドシェイクでクライアント証明書を要求して検証し、アカウント照合に `ssl_type` などを確認する検査を足す。TLS への切り替えと認証メカニズムの側は変わらない
