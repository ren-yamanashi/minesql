# 認証の方式

## Motivation

X Protocol の認証は、クライアントがメカニズム名を指定して始め、サーバーがそのメカニズムに従って資格情報を照合する。MineSQL では、どのメカニズムを提供するか、アカウントの認証プラグイン (パスワードの保存形式) を何にするか、照合をどの層で行うか、MySQL が行う検査のうち何を持つかを決める必要があった

## Decisions

- 認証メカニズムは `MYSQL41` / `PLAIN` / `SHA256_MEMORY` の 3 つを提供する
- アカウントの認証プラグインは `caching_sha2_password` のみ
- 照合は MySQL と同じ手順で行う
  - 内部セッションの実行ユーザーをシステムユーザーにして、minesql スキーマの `user` テーブルを SQL で検索する
  - 照合の計算は認証側で行い、成功したら内部セッションの実行ユーザーを認証したアカウントに切り替える
- 検査項目はパスワードの一致だけ
- 扱うアカウントは初期アカウントのみで、ホストは `%`
  - 「初期アカウントのみ」は [SDR-0017](./0017.アカウント管理ステートメントを対象に含める.md) で改め、アカウント管理ステートメントを対象に含めた (ホストが `%` だけである点は変わらない)

## Context

### 3 つのメカニズムが 1 組である理由

8.4 の既定では、アカウントは `caching_sha2_password` で、`mysql_native_password` プラグインは既定で無効になっている。この前提で 3 つのメカニズムは独立した選択肢ではなく、1 組の仕組みとして動く

- `PLAIN` は安全な接続 (Unix ソケットか TLS) でパスワードそのものを照合し、成功すると SHA256 パスワードキャッシュにそのアカウントの値を入れる
- `SHA256_MEMORY` はどの接続でも使えるが、照合先がキャッシュなので `PLAIN` で一度成功した後にしか通らない
- `MYSQL41` は `mysql_native_password` のアカウント専用で、`caching_sha2_password` のアカウントには常に access denied を返す

公式クライアントの自動選択は、安全でない接続では `SHA256_MEMORY` → `MYSQL41` の順に試す。`MYSQL41` がないと、クライアントは MySQL と違う応答 (未対応メカニズムの致命的エラー) を受ける。チャレンジレスポンスの実装は `SHA256_MEMORY` と共通なので、`MYSQL41` を持つ手間は照合器 1 つ分で済む。この結果、TLS なしの TCP では初回に `PLAIN` を使えない。TLS か Unix ソケットの接続で一度 `PLAIN` を通し、その後は `SHA256_MEMORY` で認証するという、MySQL 8.4 と同じ手順になる (TLS は [SDR-0016](./0016.TLS接続を実装する.md))

### caching_sha2_password だけにする理由

8.4 の既定であり、`mysql_native_password` は 8.4 で既定無効、`sha256_password` は非推奨だからである

### 照合を内部セッションに問い合わせる理由

データディクショナリのアカウント情報を直接読む案の方が実装は小さい。それでも MySQL と同じく SQL で `user` テーブルを検索する形にしたのは、本でアカウントの仕組みを示すためである

- システムテーブルは、同じストレージの上の普通のテーブルである
- サーバー自身が、まだ誰でもない接続のために、システムユーザーとして自分の内部セッションの実行ユーザーになる
- 「誰として SQL を実行するか」は内部セッションの状態であり、照合が通った後に切り替わる
- 起動時にサーバーが自分でシステムテーブルを作る (bootstrap)

MySQL の認証にはもう 1 つの経路がある。user@host のパターン照合と権限の判定は、`mysql.user` を起動時に読み込んだメモリ上の表 (ACL キャッシュ) が行う。MineSQL は権限をグローバル権限だけにし ([SDR-0018](./0018.権限はグローバル権限だけを持つ.md))、ホストも `%` だけなので、パターン照合が要らず ACL キャッシュを持たない。ホストのパターンを認めるときに ACL キャッシュを入れ、パターン照合もそこへ移す

### 検査項目を絞る理由

MySQL はパスワードの一致のほかに、アカウントのロック、パスワードの期限、`offline_mode` 中の非 SUPER ユーザー、TLS 要件を検査する。いずれもアカウント管理・サーバーモード・TLS という対象外の機能に付随する検査なので持たない

### 依存

認証が SQL の実行経路 (パーサー → プリペア → オプティマイザ → エグゼキュータ → ストレージエンジン) に依存するため、本の順序では SQL が動いてから認証を入れる。MySQL 自身も同じ依存を持つ (bootstrap も SQL で行われる)
