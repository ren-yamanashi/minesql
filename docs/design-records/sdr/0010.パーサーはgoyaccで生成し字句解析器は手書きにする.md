# パーサーは goyacc で生成し、字句解析器は手書きにする

## Motivation

SQL パーサーの実装手段として、手書きの再帰下降パーサーにするか、文法ファイルから生成するパーサーにするかを決める必要があった。MySQL は Bison (LALR(1) パーサー生成器) の文法ファイル `sql_yacc.yy` と、手書きの字句解析器の組み合わせである

## Decisions

- 構文解析器は goyacc で文法ファイルから生成する LALR(1) パーサーにする (MySQL の Bison と同系)
  - 文法ファイルは `sql_yacc.yy` の対応する規則を写し、規則末尾のアクションで AST ノードを作る (子が揃ってから親)
  - 演算子の優先順位宣言は `sql_yacc.yy` から転記する
  - 衝突は 0 を維持し、`%expect` は使わない
  - 生成コードはリポジトリに含め、`go generate` で再生成する
- 字句解析器は手書きにする (MySQL と同じ)
- 構文エラーの文言は MySQL の形式 (`… near '…' at line N`) に合わせ、期待していたトークンの列挙は開発時の診断にとどめる

## Context

### 評価の前提

「MySQL の構文規則を写す」([SDR-0007](./0007.SQLパーサーはMySQLの構文規則に従う.md)) を先に決めたことで、評価の軸は「規則をどれだけ忠実に、監査できる形で持てるか」になった

- yacc 系の文法なら、規則と優先順位宣言を MySQL と同じ書式のまま持てるので、`sql_yacc.yy` との対応を行単位で確かめられる
- 文法の曖昧さは生成時に衝突として検出される
  - 手書きの再帰下降には、この保証がない
- 読者が読む成果物は文法ファイルであり、MySQL の文法ファイルと並べて示せる (生成コードは読む対象にしない)

### 経緯

当初は読みやすさを理由に手書きの再帰下降を推奨した。その後「MySQL の規則を写す」と「自動生成できる / 既存の仕組みに乗る」を優先事項として確定した時点で評価し直し、goyacc に変更した。前提が変われば結論が変わる例として残しておく

### goyacc の制約

goyacc は Bison の `%empty` と `%expect` を持たない。空の選択肢は `/* empty */` と書き、衝突が出れば生成時に標準出力へ報告される。生成されるパーサーはエラー時に位置を渡さずに `Error(string)` を呼ぶだけなので、字句解析器が直前に返したトークンの位置を覚えておき、MySQL と同じ文言を組み立てる
