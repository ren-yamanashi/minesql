# SDI と information_schema は実装しない

## Motivation

MySQL 8.0 のデータディクショナリには、ディクショナリテーブルのほかに 2 つの付属物がある。定義の写しを表領域ファイルに埋め込む SDI (Serialized Dictionary Information) と、ディクショナリテーブルの上に定義された `information_schema` のビューである。データディクショナリの範囲を決めるときに、この 2 つを含めるかを決める必要があった

## Decisions

- SDI は実装しない
  - 表領域ファイルに定義の写しを書かず、写しから定義を取り出すツール (`ibd2sdi`) も持たない
- `information_schema` は実装しない
  - ディクショナリテーブルの上のビューも、それを参照するための `SHOW` 系のステートメントも持たない
- どちらも issue #120 の「やらないこと」に記載する

## Context

### SDI とは

テーブルや表領域の定義を JSON にして、そのテーブルのデータが入っている表領域ファイルの中に一緒に書いておく仕組みである。ディクショナリを失ったときに定義を取り出す最後の手段と、表領域を別のサーバーに持ち込む (transportable tablespace) ときの定義の運搬に使う。MineSQL は復旧ツールも表領域の持ち込みも持たないため、写しを書く理由がない

### information_schema とは

利用者が定義を SQL で参照するための、読み取り専用のビューの集まりである。8.0 ではディクショナリテーブルの上のビューとして実装されている。MineSQL の文法は `SHOW` もビューも持たず、ビューの機構を入れるのは範囲を大きく超える。結果として、利用者が自分のテーブルの定義を SQL で参照する手段は持たない

### 後から広げるとき

- SDI: 表領域ファイルに定義の写しを書く処理と、それを読む側を足す
  - ディクショナリ本体の形は変わらない
- `information_schema`: ビューの機構を入れたうえで、ディクショナリテーブルの上に読み取り専用のビューを定義する
  - ディクショナリテーブルが普通のテーブルである ([SDR-0019](./0019.ディクショナリテーブルはストレージエンジンのテーブルとして持つ.md)) ため、ビューの定義は SQL で書ける
