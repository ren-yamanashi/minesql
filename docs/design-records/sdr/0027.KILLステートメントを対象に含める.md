# KILL ステートメントを対象に含める

## Motivation

権限の判断 ([SDR-0018](./0018.権限はグローバル権限だけを持つ.md)) は、`KILL` ステートメントと管理コマンド `kill_client` の対象を同じアカウントの接続に限ると決めていたが、文法の範囲 ([SDR-0011](./0011.文法に含める構文の範囲.md)) に `KILL` は含まれていなかった。コネクションハンドラーの仕様も `KILL` ステートメントによる切断を書いており、含めるかどうかを決めて食い違いをなくす必要があった

## Decisions

- `KILL [CONNECTION] id` を文法と SQL コマンドに含める
  - `id` は接続の内部セッションの識別子で、`list_clients` の `sql_session` の欄で得られる値
  - 対象は同じアカウントの接続に限り ([SDR-0018](./0018.権限はグローバル権限だけを持つ.md))、自分自身の接続も対象にできる
- `KILL QUERY` (接続を残して、実行中のステートメントだけを止める) は含めない
- 管理コマンド `kill_client` は、対象が自分自身の接続なら直接閉じ、他の接続なら要求元の内部セッションで `KILL` を実行してから閉じる (MySQL と同じ)

## Context

### 含める理由

MySQL の X Plugin の `kill_client` は、他の接続に対しては SQL の `KILL` を実行する。つまり他人の接続を切る権限の判定は SQL の `KILL` ステートメントのもので、管理コマンドは SQL に還元されている。MineSQL でも `kill_client` が内部で `KILL` を実行するようにすれば、権限の判定はプリペアの入口の 1 箇所に集まり、ディスパッチャに同じ判定を持たずに済む。`KILL` を持たない案は文法が 1 規則減るだけで、代わりに `kill_client` が自前の判定を持つ

`KILL` に渡す識別子は、MySQL では `SHOW PROCESSLIST` や `CONNECTION_ID()` でも得られるが、MineSQL にはどちらもない。X Protocol の `list_clients` が接続ごとに内部セッションの識別子を返すので、それで足りる

### KILL QUERY を含めない理由

`KILL QUERY` は実行中のステートメントを中断して接続を残す。中断は、実行の各所で中断要求を確認する仕組みで、接続を閉じる `KILL CONNECTION` とは別の経路になる。接続の切断の説明には `KILL CONNECTION` で足りる

### 後から広げるとき何が変わるか

- `KILL QUERY`: 文法に選択肢を 1 つ足し、実行中のステートメントが中断要求を確認する点 (行の読み取りの繰り返しなど) を設ける
