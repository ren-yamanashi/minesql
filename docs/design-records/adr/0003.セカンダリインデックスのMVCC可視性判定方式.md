# セカンダリインデックスの MVCC 可視性判定方式

## Motivation

セカンダリインデックスのレコードに `lastTrxId` を持たせず、ページレベルでもトランザクション情報を持たない現状の設計では、セカンダリインデックスのみの検索 (`SecondaryIndexIterator.NextIndexOnly()`) で MVCC 可視性判定ができない

- `SecondaryIndexIterator.NextIndexOnly()` は `deleteMark` しかチェックしておらず、別トランザクションが未コミットの INSERT したレコードを返してしまう MVCC 違反のリスクがある
- セカンダリインデックスのみでスキャンを完結する Covering Index Scan を MVCC 安全に成立させる仕組みが必要

## Decisions

- `SecondaryRecord` に `lastTrxId` フィールドを追加し、レコード単位で可視性判定を行う
- `lastTrxId` で可視性が確定しない場合は、PK 検索でクラスタ化インデックスを引いて旧バージョン遡及で SK 一致を判定する (不可視時のフォールバック)
- 可視性判定の責務は access method の内部に閉じ込め、上位レイヤーから `ReadView` を渡さない設計とする
  - access method の検索 / 書き込み API は Transaction オブジェクトを受け取り、Transaction が保持する `ReadView` を介して可視性判定を行う
  - Transaction と Table は同じアクセスメソッド層内の独立した存在として扱い、互いに所有関係を持たない (詳細: [トランザクション - アクセスメソッドの中での位置づけ](../architecture/storage/access/transaction.md#アクセスメソッドの中での位置づけ))

## Context

### 案 1: SecondaryRecord に `lastTrxId` を持たせる

- セカンダリレコードのヘッダー領域に `lastTrxId` を含める (`[deleteMark][lastTrxId(4B)]`)
- `lastTrxId` が ReadView 上で可視なら、`deleteMark` の値で削除済みかどうかを判定する
- `lastTrxId` が不可視の場合は、PK 不変かつ SK 変更時の UPDATE で古い SK のセカンダリレコードが残っているケースを考慮し、クラスタ化インデックスを引いて旧バージョン遡及で「そのトランザクションから見て SK が一致するか」を判定する

### 案 2: SecondaryRecord に `createdTrxId` と `deletedTrxId` を持たせる

- セカンダリレコードに `createdTrxId` (INSERT した trxId) と `deletedTrxId` (softDelete した trxId、未削除なら 0) の 2 つの TrxId を持たせる
- セカンダリレコードのライフサイクルは INSERT と softDelete の 2 イベントだけ (PK 不変かつ SK 変更時の UPDATE は「古い SK の softDelete + 新しい SK の insert」に分解される) なので、2 つの TrxId だけでレコードの全可視性を SK 単体で判定できる
- `createdTrxId` 可視性で「そのレコード自体が見えるか」、`deletedTrxId` 可視性で「削除がそのトランザクションから見えているか」を独立に判定する
- PK 経路フォールバックが不要になる

### 案 3: InnoDB と同じ PAGE_MAX_TRX_ID 方式

- B+Tree のリーフページのヘッダーに `maxTrxId` (ページ内レコードを変更したトランザクションの最大 TrxId) を持つ
- INSERT / UPDATE / DELETE のたびにページの `maxTrxId` を更新する
- セカンダリ検索時は `maxTrxId < ReadView.upLimitId` ならページ全体が可視と判定でき、ページ単位で MVCC 可視性を確定できる
- InnoDB の [`lock_sec_rec_cons_read_sees`](https://github.com/mysql/mysql-server/blob/aa461240270d809bcac336483b886b3d1789d4d9/storage/innobase/lock/lock0lock.cc#L272) と同じ設計

### 結論

- 案 1 を採用する
- 本プロジェクトは「btree = キーと値の B+Tree、access = トランザクション + MVCC + アクセスメソッド」というレイヤー分離を持っており、btree が Trx の知識を持たないことを設計原則としている。案 3 (InnoDB の PAGE_MAX_TRX_ID 方式) は btree のページヘッダーが Trx の知識を持つため、このレイヤー分離に合わず採用できない
- 案 2 (createdTrxId + deletedTrxId) は SK 単体で可視性判定が完結するメリットがあるが、本プロジェクトは InnoDB を参考モデルとしており、InnoDB の設計思想は「履歴は PK に集約し、SK は最新状態のみ持ち、判定が確定しない場合は PK 経路フォールバック」というレイヤー化された判定であるため、案 2 はこれに揃わない (案 1 はこれに従う)

### 不可視時の PK 経路フォールバック

PK 不変かつ SK 変更時の UPDATE では、古いセカンダリレコードは `deleteMark=1, lastTrxId=新Trx`、新しいセカンダリレコードは `deleteMark=0, lastTrxId=新Trx` となる。新Trx が不可視のトランザクションから見ると以下を満たす必要がある

- 新しいセカンダリレコード (新 SK) は見えない (新Trx 不可視)
- 古いセカンダリレコード (古い SK) は見える (古い行は新Trx 以前の状態として残っているはず)

`lastTrxId` 単体での可視性判定だけ行うと、古いセカンダリレコードの `lastTrxId=新Trx` が不可視となり「古い SK が見えない」というバグになる。これを避けるため

1. `lastTrxId` が ReadView 上で可視 → `deleteMark` の値で削除済みかどうかを判定する (SK 単体で確定する経路)
2. `lastTrxId` が不可視ならクラスタ化インデックスを引いて、PK に対応するレコードを旧バージョン遡及で取得する
3. 旧バージョンで再構築した行のカラム値が、セカンダリレコードの SK と一致するなら「そのトランザクションから見て SK が一致する」と判定し可視扱い
4. 一致しないなら不可視 (UPDATE で SK が変わっていた)

このフォールバックロジックは [`PrimaryIndexIterator.resolveVisible`](../../internal/storage/access/iterator_primary_index.go) と類似だが、最終目的が「SK 一致判定」である点が異なる

## Result

本リファクタで Transaction オブジェクトを導入し、ReadView の所有者を Transaction に変更した。検索 / 書き込み API は Transaction を引数で受け取る形に統一し、TrxManager と TrxId を別々に受け取る形を取り除いた。Transaction は自分を生成した TrxManager への参照を持ち (DI の延長として扱う)、検索内部から ReadView を遅延作成する
