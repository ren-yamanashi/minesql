# Redo ログ末尾の不完全レコード扱い

## Motivation

Redo ログ末尾に残る書きかけの不完全レコードについて、 doc は「次回追記で上書きされる」 と説明しているが、 実装はその挙動を保証しておらず、 次回読み込みで破損扱いになる可能性がある。 不完全末尾の扱いを実装と doc の両方で整合させる方針を確定させる

## Decisions

- 起動時の Redo ログ読み込みでは、 不完全末尾を検知したら有効レコード末尾のオフセットをメモリ上に記録する。 ファイル物理操作 (= truncate) は行わない
- 追記時には、 記録した有効レコード末尾オフセットへ seek してから書き込みを開始する。 これにより端数バイトが新レコードで物理的に上書きされる
- doc 記述「次にレコードを追記したときにそのまま上書きされる」 はこの実装に整合する

## Context

### 前提

Redo ログレコードの追記中にクラッシュすると、 ファイル末尾には書きかけの不完全なバイト列 (= レコードヘッダーに満たない端数バイト) が残ることがある

[redo.md - クラッシュ時の末尾レコードの扱い](../architecture/storage/log/redo.md#クラッシュ時の末尾レコードの扱い) では「書きかけのレコードとして無視する。 次にレコードを追記したときにそのまま上書きされるため、 データ整合性には影響しない」 と説明されているが、 実装は次の状態にある

- 起動時の読み込みは末尾の端数を検出して break するが、 ファイルサイズを切り戻す処理はない
- 次回の追記は `Seek(0, io.SeekEnd)` で物理ファイル末尾に書くため、 端数の後ろに新レコードが書き足される
- この状態で再度起動すると、 端数と後続レコードが連結された位置からデコードされ、 残りバイト数がレコードヘッダー以上になりうるため破損扱いになる可能性がある

つまり「doc の論理的な意図」 と「実装の物理的な動作」 が乖離しており、 doc の前提条件 (= 端数が次回追記で消える) が実装では成立していない

### 案 1: 読み込み時に有効レコード末尾まで truncate する

- 起動時の読み込みで不完全末尾を検知した瞬間に、 ファイルサイズを有効レコード末尾まで切り戻す
- 起動後は「ファイルサイズ = 有効データ末尾」 という不変条件が常に成立し、 以降の追記は SeekEnd でそのまま正しい位置に書ける
- 端数バイトは物理的にファイルから消える
- 追加状態 (= 「有効末尾オフセット」 のフィールド) を持つ必要がない

### 案 2: 追記時に有効レコード末尾オフセットへ seek する

- 起動時の読み込みは純粋な read として行い、 有効レコード末尾のオフセットだけをメモリ上のフィールドに記録する
- 物理ファイルには端数バイトが残ったままになる
- 追記時に記録したオフセットへ seek してから書き込みを開始することで、 端数バイトを新レコードで上書きする
- 「ファイルサイズ ≠ 有効レコード末尾」 の状態を明示的なフィールドで区別する

### 評価基準

- doc 記述との整合 (= 既存 doc の「次にレコードを追記したときにそのまま上書きされる」 表現と直接対応するか)
- Command-Query Separation の原則 (= 読み込みは副作用なし、 副作用は書き込み側に局所化)
- 状態の明示性 (= ファイル状態の意味が clear に表現されるか)
- InnoDB との整合 (= 参考モデル MySQL/InnoDB が同等の課題でどう実装しているか)
- 実装シンプルさ (= 追加状態の管理コスト)
- I/O コスト (= 起動時の余分な fsync 等)

### 評価結果

| 観点 | 案 1 (= 読み込み時 truncate) | 案 2 (= 追記時 seek) |
| --- | --- | --- |
| doc 整合 | △ (= 読み込み時に端数が消えるため doc の「追記時に上書き」 表現と微妙にずれる) | ◎ (= doc 記述と直接整合) |
| Command-Query Separation | × (= 読み込みに副作用 = truncate が発生) | ◎ (= 読み込みは純粋 read) |
| 状態の明示性 | △ (= 「ファイルサイズが有効末尾を表す」 という暗黙ルール) | ◎ (= 有効末尾オフセットを明示的フィールドで保持) |
| InnoDB との整合 | × (= InnoDB は物理操作なし、 メモリで有効末尾管理) | ◎ (= InnoDB と同方針) |
| 実装シンプルさ | ◎ (= 追加状態なし) | ○ (= 1 フィールド追加) |
| I/O コスト | △ (= 起動時に truncate + fsync が発生) | ◎ (= 起動時の余分な I/O なし) |

### InnoDB の実装根拠 (= 案 2 と同方針)

InnoDB の Redo log は不完全末尾を検知してもファイル物理操作を行わず、 メモリ上で有効末尾 LSN を管理し、 次回書き込みで上書きする方針を取っている

[log0recv.cc:3408-3414](https://github.com/mysql/mysql-server/blob/trunk/storage/innobase/log/log0recv.cc) — 不完全ブロック検出時のコメント

> Garbage or an incompletely written log block. We will not report any error, because this can happen when InnoDB was killed while it was writing redo log. We simply treat this as an abrupt end of the redo log.

[log0log.cc:795-796](https://github.com/mysql/mysql-server/blob/trunk/storage/innobase/log/log0log.cc) — 不完全末尾の論理的補正

> The last mtr in the block might have been incomplete, thus we trim the block to the start_lsn which is the end of the last mtr found in recovery.

InnoDB はメモリ上の `scanned_lsn` / `write_lsn` で有効末尾を追跡し、 次回書き込みのオフセットを `LOG_FILE_HDR_SIZE + (LSN - file_start_lsn)` で計算する。 ファイルサイズ自体に「有効末尾」 の意味を持たせていない

### 結論

- 案 2 を採用する
- 案 1 は「不変条件 (= ファイルサイズ = 有効末尾) のシンプルさ」 「状態追加なし」 という独自の利点があるが、 以下の理由で案 2 に劣る
  - 本プロジェクトは InnoDB を参考モデルとしており、 案 2 が InnoDB の方針と整合する
  - Command-Query Separation の原則に合致 (= 読み込みに副作用がない)
  - 既存 doc 記述「次にレコードを追記したときにそのまま上書きされる」 と直接対応する
  - 「ファイルサイズ ≠ 有効末尾」 を明示的なフィールドで区別することで、 ファイル状態の意味が単一視点で表現される (= 「ファイルサイズが何を意味するか」 の解釈が不要)
