# 仕様書の思想

`docs/specification/` 配下の仕様書を書く / 読むときの前提となる方針。X Protocol とコネクションハンドラーの仕様を整理する過程で確定した判断をまとめたもので、以後の仕様書にも同じ方針を適用する

- この文書は育てていくもので、今後の仕様整理の過程で新たに学んだ思想や、固まったスコープ (実装する / しないの判断) は、確定した時点でこの文書に追記する
- 追記するときは、判断そのものだけでなく理由も書く (後から見返したときに、前提が変わっていないか判断できるようにするため)

## 目的とスコープ

- 目的
  - minesql は MySQL (InnoDB) を参考モデルにして、小さい MySQL をゼロから作る学習用の RDB
  - 最終的には「作って学ぶ MySQL」(仮) のようなオンラインブックとしてまとめる予定で、仕様書はその下敷きになる
  - そのために、MySQL 8.4 の X Protocol / X Plugin の挙動を「実装の根拠にできる精度」で整理する
- 読者を意識する
  - 仕様書は自分たちの実装メモであると同時に (それを精査したもの) 本の読者が読む可能性があるものなので、MySQL の内部を初めて読む人が追える順序と語彙で書く
  - 以下の「文書の構成」「書き方」「図」の規則は、この読者を想定して決めている
- スコープが狭いことと、拡張可能性を考慮しないことは別 (2026-09-12 確定)
  - 何かを対象外にする判断では「対象外だから不要」で終わらせず、後から入れる場合に何が変わるか (どの約束を守っていれば追加だけで済むか) を併記する
  - 例: SQL パーサーが parse tree と文脈化を持たないのは、サブクエリや HAVING を諦めたからではなく、「ノードは周囲を知らずに作れる」「周囲に依存する判断はプリペアで行う」という約束を守れば、両者は文法とプリペアの追加だけで足せるため
  - 理由: 本の実装は段階的に育てるものなので、初期のスコープで下した判断が後の章の足かせにならないようにする
- 正とするもの: ローカルの mysql-server 8.4 (commit `aa461240`)
  - プロトコルは `.proto` ファイル、サーバーの挙動は `plugin/x/src` を正とする
  - マニュアル・WL・公式ブログは理解の入口であり、最終的な根拠にはしない
- 実装対象は X Protocol を話すサーバー、つまり X Plugin に相当する層 (コネクションハンドラー + プロトコル処理 + セッション + SQL 実行への橋渡し)
  - classic protocol は実装対象外で、対比のために触れる程度にとどめる (X Protocol の接続はサーバー本体の classic 用コネクションハンドラーを通らない)
- ドキュメントモデル (コレクション、CRUD メッセージ、管理コマンド、JSON 型) は実装しない
  - 理由 1: SQL の上のレイヤーで、プロトコルの中核 (フレーム、capability、認証、シーケンス、SQL 実行と結果セット、Notice、セッションリセット) から独立している (CRUD → SQL 変換として実装されている)
  - 理由 2: `.proto` ファイル単位で綺麗に切り離せる
    - `mysqlx_crud.proto` と `mysqlx_expr.proto` を丸ごと省ける
    - `StmtExecute` の引数は `Mysqlx.Datatypes.Any` で、式木に依存しない
  - 理由 3: RDB の内部構造を理解するという目的に直交する付加機能で、省いても学びが欠けない
  - 仕様書では「X Plugin の機能の 1 つ」という位置づけの説明にとどめ、詳細は書かない
  - 境界
    - 未対応のメッセージにはエラーを返す (X Plugin は認証前なら FATAL の `ER_X_BAD_MESSAGE` で接続を閉じ、認証後なら通常エラーの `ER_UNKNOWN_COM_ERROR` を返してセッションを継続する)
- X Protocol のプリペアドステートメントとカーソル (`Mysqlx.Prepare` / `Mysqlx.Cursor`) は実装しない (2026-09-08 確定、やらないことリストの issue #120 に記載)
  - 理由 1: 往復回数を減らすための最適化機能で、クライアントは `StmtExecute` だけで同じ操作ができる
  - 理由 2: specification/ の `prepare/` はコア側の準備フェーズ (`Sql_cmd_dml::prepare`) を指しており、プロトコル側のプリペアドステートメントとは別物
  - 未対応のメッセージとしてエラーを返す
- Expect ブロック (`Mysqlx.Expect.Open` / `Close`) は実装する (2026-09-08 確定)
  - 理由: パイプライン化 (X Protocol の主要な特徴) で依存する要求の失敗を扱うために必要で、実装はセッションごとのスタックと `no_error` 条件だけで小さい
- 管理コマンド (`StmtExecute` の `mysqlx` namespace) は `ping` / `list_clients` / `kill_client` と Notice 系の `enable_notices` / `disable_notices` / `list_notices` の 6 つを実装し、コレクション系の 8 つ (`create_collection` / `drop_collection` / `ensure_collection` / `modify_collection_options` / `get_collection_options` / `create_collection_index` / `drop_collection_index` / `list_objects`) は実装しない (2026-09-08 確定)
  - 理由 1: コレクション系はドキュメントモデルの管理コマンドで、ドキュメントモデルを実装しない判断に従う
  - 理由 2: Notice 系は Notice の仕組みそのものではなく「どの種類の Notice を送るか」(既定で有効な警告と、グループレプリケーション関連) をセッション単位で切り替えるだけの機能で、実装はセッションごとのフラグで済む
  - 理由 3: `ROWS_AFFECTED` や `ServerHello` などの Notice はこの設定と無関係に送られるため、Notice 系コマンドの有無で Notice の機能は左右されないが、警告 Notice を実装する以上その抑止手段も揃えておく
- コアサーバーの `COM_*` 層 (`dispatch_command`) は minesql には作らない (2026-09-08 確定)
  - 理由: `COM_*` は classic protocol のコマンド種別であり、X Plugin がこの層を使うのは SQL 層に頼みたい操作 (文の実行、セッション状態のリセット、既定スキーマの切り替え、プリペアド系) を翻訳して渡すためにすぎない
    - classic を持たない minesql ではディスパッチャが SQL 層に直接依頼すればよい
  - 仕様書では委譲先を「SQL 層 (内部セッション)」と抽象化して書き、command service と `dispatch_command` の対応は詳細仕様の 1 節にとどめる
- SQL パーサーの構文互換: 対応するステートメント (SELECT / INSERT / UPDATE / DELETE / CREATE TABLE / トランザクション制御など) については、MySQL の構文規則 (`sql_yacc.yy` の対応する規則、字句規則、演算子の優先順位) にできるだけ従う (2026-09-11 確定)
  - サブクエリは対応しない (issue #120)
  - 従う意味がない構文 (minesql が実装しない機能に付随する句、後方互換のためだけの別表記) は受理せず、どこを外したかは仕様書に理由つきで記録する
  - 理由: 公式クライアントや利用者が MySQL の常識どおりに書いた SQL をそのまま受理できることが、「小さい MySQL」であることの外から見える条件になる
- SQL パーサーの責務は「ステートメントの文字列 → AST」まで (2026-09-11 確定)
  - AST は句の単位 (SELECT なら選択リスト / FROM / WHERE / ORDER BY / LIMIT) で構成し、構文上の同義語 (`<>` と `!=`、`JOIN` と `INNER JOIN` など) はパーサーで吸収する
  - MySQL が `parse_sql` の中で行う文脈化 (parse tree から `Query_block` / `Item` を組み立てる段階) は持たない
  - 名前解決・型決定・データディクショナリの参照・クエリの変換はプリペア以降の責務
  - AST は MySQL の `Query_block` / `Item` に相当する構造を未解決の状態で作ったもので、プリペアが同じノードに解決結果を書き込み、最適化と実行も同じ構造を使う (2026-09-12 確定)
    - パーサーは解決結果の欄に書かず、解決済みかどうかは明示的な印で表し、最適化と実行は解決済みのノードだけを受け取る
    - 理由: 「アーキテクチャと概念は MySQL に忠実」の軸で、プリペア以降が触る構造こそ読者が MySQL のソースと突き合わせる部分であるため
    - 検討した代替: 構文木と解決済みの構造を別に持つ案は、同じ文を解き直す機能 (プリペアドステートメント、ビュー) で有利だが、どちらも対象外
    - サブクエリや HAVING を後から入れる場合も、「ノードは周囲を知らずに作れる」「周囲に依存する判断はプリペアで行う」を守れば文法とプリペアの追加で済む
  - パーサーの出口は、AST をステートメント種別ごとの実行コマンド (MySQL の `Sql_cmd` 相当で、`prepare` と `execute` の入口を持つ) に包んだもの (2026-09-12 確定)
    - SQL 層の入口は「パースして実行コマンドを受け取り、`prepare` → `execute` を呼ぶ」だけで、種別の switch を持たない (MySQL の `mysql_execute_command` にある switch は `Sql_cmd` への移行途中の名残)
    - 種別から実行コマンドへの対応は還元された文法規則だけで決まり、文脈もデータディクショナリも読まないため、パーサーの文脈非依存は保たれる
    - 検討した反対意見: 「パーサーは文字列 → AST に限るべき」という責務の純度
      - 対応が構文だけで決まり意味の判断が入らないため、越権にはならないと判断した
  - 理由 1: MySQL の parse tree と文脈化は、生まれる時点で周囲 (所属するクエリブロック、外側のクエリ、文中の位置) を必要とする旧来の構造と、ボトムアップ解析の順序との衝突を解くためのもので、minesql の構造は周囲を知らずに作れるため不要
  - 理由 2: 文法規則の末尾のアクションで句の単位の AST を直接作れるため、組み替えの段階が不要
  - 理由 3: パーサーがデータディクショナリやセッションを読むと、同じ文字列から異なる AST が出る (文脈依存) 設計に戻る
- SQL パーサーの実装手段は goyacc で生成する LALR(1) パーサーとし、字句解析器は手書きにする (2026-09-11 確定)
  - 文法ファイルは `sql_yacc.yy` の対応する規則を写し、規則末尾のアクションで AST ノードを作る (子が揃ってから親)
  - 演算子の優先順位宣言は `sql_yacc.yy` から転記する
  - 衝突は 0 を維持する (`%expect` を使わない)
  - 構文エラーの文言は MySQL 形式 (`… near '…' at line N`) に合わせ、期待トークンの情報は開発時の診断用にとどめる
  - 生成コードはリポジトリに含め、`go generate` で再生成する
  - 理由 1: 「MySQL の構文規則を写す」方針の下では、規則と優先順位宣言をそのままの形で持てる yacc 系の文法が最も忠実で、`sql_yacc.yy` との対応を行単位で監査できる
  - 理由 2: 文法の曖昧さを生成時に衝突として検出でき、手書きの再帰下降にはこの保証がない
  - 理由 3: 読者が読む成果物は文法ファイルであり、MySQL の文法ファイルと同じ書式なので本の中で並べて示せる (生成コードは読む対象にしない)
  - 経緯: 当初は読みやすさから手書きの再帰下降を推奨したが、「MySQL の規則を写す」と「自動生成できる / 既存の仕組みに乗る」を優先事項として確定した時点で評価し直し、goyacc に変更した
- SQL パーサーの文法には、minesql が実装していない機能の構文を含めず、構文エラーにする (2026-09-11 確定)
  - 含めるかどうかは「実装コスト」と「MySQL の仕組みを説明するうえでの重要度」で個別に判断する
  - 含めないもの: GROUP BY / HAVING / 集約関数 / LEFT・RIGHT JOIN / UNION / NULL / 関数呼び出し / VARCHAR 以外の型 / TEMPORARY / スキーマ修飾 / テーブルオプション (issue #120 の「やらないこと」と一致)
  - 例外として含めるもの (2026-09-11 確定、issue #120 の「やらないこと」から ORDER BY と LIMIT を外した): SELECT の ORDER BY と LIMIT、`START TRANSACTION WITH CONSISTENT SNAPSHOT`、`SELECT ... FOR UPDATE` と `SELECT ... FOR SHARE` (同義語 `LOCK IN SHARE MODE`)
    - 理由: いずれも実装が小さく (LIMIT は件数のカウンタ、ORDER BY はインデックス順の走査かソートで満たす、CONSISTENT SNAPSHOT はトランザクション開始時の ReadView 作成、FOR UPDATE / FOR SHARE は読み取り時の排他ロック / 共有ロック)、クラスタ化インデックス・MVCC・ロックの説明に直結する
  - ファイルソート (ORDER BY をインデックスの順序で満たせないときのソートで、ソートバッファ内のソートと、収まらない場合のディスクへの書き出しとマージ) も実装する (2026-09-11 確定、issue #120 の「やらないこと」から外した)
    - 理由: インデックス順で済ませるかソートするかという最適化の判断と、クエリ実行の仕組みを説明する題材になる
    - 段階の切り方 (メモリ内ソート → ディスクへの書き出し) は実装計画で決める
  - UPDATE / DELETE の `ORDER BY ... LIMIT` は含めない (2026-09-11 確定)
    - 理由: 標準 SQL にない MySQL 拡張で用途が運用寄りであり、更新・削除の経路に「並べて絞った行の供給」を足す別の実装が要る
  - 理由 1: パーサーが受理する構文と実行できる機能を一致させ、誰も消費しない AST ノードとプリペア側の拒否処理を持たない
  - 理由 2: 本の中核は InnoDB (ストレージ) になる見込みで、これらの構文の重要度は高くない
  - 外した構文は詳細仕様 (`parser/reference/sql_parser_spec.md`) に MySQL の規則の permalink つきで記録してあるため、実装すると決めた時点で表の行を「採用」に変えて規則を写せばよい
- SQL パーサーのキーワード表は、minesql の文法に現れる語だけにする (2026-09-11 確定)
  - 予約語 / 非予約語の区分は MySQL の `ident_keyword` に従い、非予約語は識別子としても受理する
  - MySQL の予約語でも minesql の文法に現れない語は識別子として扱う
  - 理由: MySQL で通る SQL は minesql でも通る向きの互換が保たれ、字句解析器が文法で使わない語を持たずに済む
- SQL パーサーでは `sql_mode` に依存する字句・構文の分岐を 8.4 の既定値に固定する (2026-09-11 確定)
  - `"` は文字列の引用符、バックスラッシュエスケープは有効、`NOT` は低い優先順位、`||` は採用しない
  - 理由: minesql は `sql_mode` を持たず、既定値以外の挙動を選べる必要がない
- 8.4 で非推奨の別表記 (`&&`、`||`、`!`、`$` で始まる識別子、`N'...'`、`BINARY expr`、`INSERT DELAYED`、`SQL_CALC_FOUND_ROWS`) と、MySQL 自身が読み飛ばす構文 (列定義内の `REFERENCES`、外部キーの `MATCH`、`DROP TABLE ... RESTRICT | CASCADE`) は採用しない (2026-09-11 確定)
  - 理由: 従っても挙動が変わらない、または将来の MySQL で消える構文に互換を保つ意味がない

## 文書の構成

- 読む順で分ける: 概要 (位置づけ) → 論理モデル / 流れ (2026-09-12 変更: 詳細仕様は読む順に含めない)
  - ディレクトリごとに README を置き、読む順と各文書の内容を示す
  - protocol/: `x_protocol.md` (概要) → `communication_flow.md` (流れ) → `message_spec.md` (詳細)
    - `message_spec.md` は外部との契約 (メッセージ定義とエンコーディング) で minesql の判断で変わらないため、他の詳細仕様と違って読む順に含める (2026-09-12 確定)
  - connection/: `x_plugin.md` (要件) → `connection_handler.md` (論理モデル)、詳細は `reference/connection_handler_spec.md`
  - parser/: `sql_parser.md` (論理モデル)、詳細は `reference/sql_parser_spec.md`
  - X Plugin 全体の要件 (`x_plugin.md`) は connection/ に置いたままにし、dispatcher/ からは connection/ の文書を参照する (2026-09-08 確定)
- 論理モデル側に書くこと: 責務 (担うこと / 担わないこと)、構成要素 (状態と寿命を持ち振る舞いの主体となるもの)、実行モデル (スレッド)、処理の流れ、状態遷移、守る境界の種類
  - 数値・条件・カウンタ・ソースの細部は書かない
- 詳細仕様側に書くこと: 時系列に沿った具体的な処理と条件、既定値、状態変数、設定変数の表
  - 主張ごとにソースの参照を付ける
  - 詳細仕様のうち MySQL の実装内部の対応表 (connection / dispatcher / parser の `xxx_spec.md`) は `<domain>/reference/` に置き、README では「実装時の参照資料」として触れるだけで読む順に含めない (2026-09-12 確定)
    - 外部との契約 (protocol の `message_spec.md`) は要件そのものなので、この扱いの対象外
  - 書く / 更新するのは、そのドメインを実装する段階にする
    - 要件と論理モデルが固まる前に書くと、判断が変わるたびに書き換えになるため (ORDER BY / LIMIT や FOR SHARE の判断で実際に起きた)
  - 論理モデルと食い違う場合は論理モデルを正とする
  - 理由: 詳細仕様は MySQL のコードとの対応表で、本の本文にはならず、実装の根拠と「MySQL ではこうなっている」という補足の材料として使うもの
- 依存の向き: 詳細 → 論理 (状態図などの定義を参照)、論理 → 詳細 (節単位で参照)
  - 同じ対応関係を 2 箇所に持たない (図と表が同じ対応を表すなら片方に寄せる)
- 冒頭は位置づけだけを書く
  - 用語の定義はその語の初出の場所に置く
- 名前の付け方: ディレクトリ名はサーバーのコンポーネント名 (connection / dispatcher / parser …)、ファイル名は責務名 (`connection_handler.md`)、README の題は対象の名前 (「コネクションハンドラーの仕様」)
  - 層を表す造語 (「接続層」など) は使わない

## 書き方

- 用語は [glossary.md](./glossary.md) の「採用する語」に従い、新しい語を導入するときは glossary に追加する (2026-09-09 確定)
  - 理由: 本にしたときに用語の揺れが最も目立つため、辞書を正として揃える
- 論理名で書き、実装名は括弧で添える: 接続 (Client)、セッション (Session)、内部セッション (THD)
  - 実装の命名が論理名と衝突する場合 (X Plugin は接続 1 本を表すオブジェクトを Client と呼ぶ) は、その旨を注記する
- 構成要素は「何を持つか」ではなく「何に責任を持つか / 何を決めるか」「いくつ存在し、いつ生まれていつ消えるか」「他の要素とどう関係するか」で説明する
- 造語を避ける
  - 「コアサーバー」「接続層」のような語を作らず、文脈ごとの平易な言い方 (「サーバー全体の `max_connections`」「内部セッション」) にする
- 因果で書く
  - classic protocol との違いは「制約 → 解消 → 効果」、性質は「前提 → 帰結」の形にする
  - 前提の置き場がない「帰結」を作らない
- 物理名の扱い
  - 図のノードや本文は論理名で書き、ソケット API に対応する段階だけ括弧で物理名を添える (socket / bind / listen、accept、recv / send、close)
  - プロトコルのメッセージ名 (`ServerHello`、`AuthenticateStart` など) は日本語に言い換えず、そのまま使う (「挨拶の通知」のような訳は不自然になる)
- 根拠の付け方
  - 主張ごとにソースへの permalink (コミット固定 + 行範囲) を付ける
  - 行番号はローカルのソースで確認したものだけを書く
  - 「参照:」は入れ子の bullet にし、1 リンク 1 行で書く
  - 検証していないことは「未検証」と明示する (ビルド時定義の既定値、スレッド数の断定など)
- 箇条書きの規則
  - bullet 内で「。」を使わず、続きの文は入れ子の bullet に分ける
  - 全角と半角の間にスペースを入れ、括弧は半角にする
  - MUST / SHOULD は文末表現 (〜なければならない / 〜べきである) で表し、ラベルと文末を混在させない
- 翻訳 (WL の要件など) は原文に忠実にし、要件の追加も削除もしない
  - 原文の古い名称 (getCapabilities) には現行名 (`CapabilitiesGet`) を注記する

## 図

- 1 つのモデルを複数の見方で描き、役割を重複させない
  - sequenceDiagram は「誰と誰がやり取りするか」
  - flowchart は「段階と分岐」
  - stateDiagram は「状態と遷移」
- 参加者名は誤認を避ける
  - プロトコルの図 (protocol/) では、プロトコルの端点として「クライアント」「サーバー」と書く
  - X Plugin 内部の要素「接続 (Client)」が同じ図に登場する場合 (connection/) は、接続元を「クライアントプログラム」と書いて区別する
- 図の中の境界: box で「クライアント側 / サーバー側 › X Plugin / サーバー側 › X Plugin の外」を分け、X Plugin が mysqld と同じプロセス内にあることを Note で示す (mermaid の box は入れ子にできない)
- 概念モデル (`docs/model/`) の語彙 (接続、セッション) と仕様書の論理名を一致させる

## 用語

- X Protocol: 通信規約
  - フレーム + protobuf メッセージの規約そのもので、`.proto` ファイルが仕様の正
- X Plugin: サーバー側の実装
  - X Protocol を待ち受け、接続処理・capability・認証・Notice・SQL 実行・ドキュメントモデルを担う
  - mysqld と同じプロセスで動く
- X DevAPI: クライアント側の API 仕様
  - MySQL Shell や各言語の Connector が実装し、内部で X Protocol を話す
- コネクションハンドラー: X Plugin のうち、接続の受付からセッションの確立・切断までを担う部分
  - minesql では X Plugin 型のハンドラーを 1 つ作ればよく、classic 用のハンドラーに相当するものは不要
- 内部セッション: 利用者の身元と実行状態を持ち、その利用者として SQL を実行する SQL 層側の場
  - 実装上は THD で、X Plugin のセッションと 1 対 1 に対応する
