# 仕様書の思想

`docs/specification/` 配下の仕様書を書く / 読むときの前提となる方針 (思想)。仕様を整理する過程で固まったもので、以後の仕様書にも同じ方針を適用する

- この文書は育てていくもので、仕様整理の過程で新たに学んだ思想は、確定した時点でこの文書に追記する
- 実装する / しないの判断と、その理由・比べた案・経緯は、この文書ではなく [adr/](./adr/README.md) に 1 判断 1 ファイルで記録する
  - 仕様書には「何を満たすか」だけを書き、判断の経緯を書かない

## 目的とスコープ

- 目的
  - minesql は MySQL (InnoDB) を参考モデルにして、小さい MySQL をゼロから作る学習用の RDB
  - 最終的には「作って学ぶ MySQL」(仮) のようなオンラインブックとしてまとめる予定で、仕様書はその下敷きになる
  - そのために、MySQL 8.4 の X Protocol / X Plugin の挙動を「実装の根拠にできる精度」で整理する
- 読者を意識する
  - 仕様書は自分たちの実装メモであると同時に (それを精査したもの) 本の読者が読む可能性があるものなので、MySQL の内部を初めて読む人が追える順序と語彙で書く
  - 以下の「文書の構成」「書き方」「図」の規則は、この読者を想定して決めている
- スコープが狭いことと、拡張可能性を考慮しないことは別 (2026-09-12 確定)
  - 何かを対象外にする判断では「対象外だから不要」で終わらせず、後から入れる場合に何が変わるか (どの約束を守っていれば追加だけで済むか) を併記する
  - 例: SQL パーサーが parse tree と文脈化を持たないのは、サブクエリや HAVING を諦めたからではなく、「ノードは周囲を知らずに作れる」「周囲に依存する判断はプリペアで行う」という約束を守れば、両者は文法とプリペアの追加だけで足せるため
  - 理由: 本の実装は段階的に育てるものなので、初期のスコープで下した判断が後の章の足かせにならないようにする
- 正とするもの: ローカルの mysql-server 8.4 (commit `aa461240`)
  - プロトコルは `.proto` ファイル、サーバーの挙動は `plugin/x/src` を正とする
  - マニュアル・WL・公式ブログは理解の入口であり、最終的な根拠にはしない
- スコープの要点 (判断ごとの理由と経緯は [adr/](./adr/README.md))
  - 実装対象は X Protocol を話すサーバー (X Plugin に相当する層) で、classic protocol は対比にとどめる ([ADR-0001](./adr/0001.実装対象はXProtocolを話すサーバー.md))
  - 実装しないもの: ドキュメントモデル ([ADR-0002](./adr/0002.ドキュメントモデルは実装しない.md))、プロトコルのプリペアドステートメントとカーソル ([ADR-0003](./adr/0003.プロトコルのプリペアドステートメントとカーソルは実装しない.md))、classic の COM コマンド層 ([ADR-0006](./adr/0006.classicのCOMコマンド層は作らない.md))
  - 実装するもの: Expect ブロック ([ADR-0004](./adr/0004.Expectブロックを実装する.md))、接続系と Notice 系の管理コマンド 6 つ ([ADR-0005](./adr/0005.管理コマンドは接続系とNotice系の6つを実装する.md))、TLS 接続 ([ADR-0016](./adr/0016.TLS接続を実装する.md))
  - SQL パーサー: MySQL の構文規則に従う ([ADR-0007](./adr/0007.SQLパーサーはMySQLの構文規則に従う.md))、出力は未解決のクエリブロックと式で文脈化を持たない ([ADR-0008](./adr/0008.パーサーの出力は未解決のクエリブロックと式で文脈化を持たない.md))、出口は実行コマンド ([ADR-0009](./adr/0009.パーサーの出口は実行コマンドに包む.md))、goyacc で生成し字句解析器は手書き ([ADR-0010](./adr/0010.パーサーはgoyaccで生成し字句解析器は手書きにする.md))、文法に含める構文の範囲 ([ADR-0011](./adr/0011.文法に含める構文の範囲.md))、キーワード表は文法が使う語だけ ([ADR-0012](./adr/0012.キーワード表は文法が使う語だけにする.md))、`sql_mode` の既定値に固定し非推奨と無視される構文は採らない ([ADR-0013](./adr/0013.sql_modeの既定値に固定し非推奨と無視される構文は採らない.md))
  - スキーマを持ち、システムスキーマ `mysql` にシステム表を置く ([ADR-0014](./adr/0014.スキーマを持つ.md))
  - 認証は 3 メカニズム、`caching_sha2_password` のみ、`mysql.user` を SQL で引いて照合する ([ADR-0015](./adr/0015.認証の方式.md))
  - 上記以外の「やらないこと」は [issue #120](https://github.com/ren-yamanashi/minesql/issues/120) が正

## 文書の構成

- 読む順で分ける: 概要 (位置づけ) → 論理モデル / 流れ (2026-09-12 変更: 詳細仕様は読む順に含めない)
  - ディレクトリごとに README を置き、読む順と各文書の内容を示す
  - protocol/: `x_protocol.md` (概要) → `communication_flow.md` (流れ) → `message_spec.md` (詳細)
    - `message_spec.md` は外部との契約 (メッセージ定義とエンコーディング) で minesql の判断で変わらないため、他の詳細仕様と違って読む順に含める (2026-09-12 確定)
  - connection/: `x_plugin.md` (要件) → `connection_handler.md` (論理モデル) → `authentication.md` (認証)、詳細は `reference/connection_handler_spec.md`
  - parser/: `sql_parser.md` (論理モデル)、詳細は `reference/sql_parser_spec.md`
  - X Plugin 全体の要件 (`x_plugin.md`) は connection/ に置いたままにし、dispatcher/ からは connection/ の文書を参照する (2026-09-08 確定)
- 論理モデル側に書くこと: 責務 (担うこと / 担わないこと)、構成要素 (状態と寿命を持ち振る舞いの主体となるもの)、実行モデル (スレッド)、処理の流れ、状態遷移、守る境界の種類
  - 数値・条件・カウンタ・ソースの細部は書かない
  - ソースコードへの行番号つきのリンクは置かない (2026-09-12 確定)
    - 主張の根拠は同じドメインの reference 文書の「論理モデルの主張とソースの対応」に置き、論理モデルからは冒頭で 1 度だけそこへ案内する
    - MySQL の設計文書 (WL、公式ブログ、`.dox`) や外部資料は、文末の「参考資料」に行番号なしで列挙する
    - 理由: 論理の文書は読者が流れで読むもので、bullet ごとの permalink は書き手の証拠置き場になり読みを妨げる
- 詳細仕様側に書くこと: 時系列に沿った具体的な処理と条件、既定値、状態変数、設定変数の表
  - 主張ごとにソースの参照を付ける (ソースへの permalink はこちらだけに置く)
  - 詳細仕様のうち MySQL の実装内部の対応表 (connection / dispatcher / parser の `xxx_spec.md`) は `<domain>/reference/` に置き、README では「実装時の参照資料」として触れるだけで読む順に含めない (2026-09-12 確定)
    - 外部との契約 (protocol の `message_spec.md`) は要件そのものなので、この扱いの対象外
  - 書く / 更新するのは、そのドメインを実装する段階にする
    - 要件と論理モデルが固まる前に書くと、判断が変わるたびに書き換えになるため (ORDER BY / LIMIT や FOR SHARE の判断で実際に起きた)
  - 論理モデルと食い違う場合は論理モデルを正とする
  - 理由: 詳細仕様は MySQL のコードとの対応表で、本の本文にはならず、実装の根拠と「MySQL ではこうなっている」という補足の材料として使うもの
- 依存の向き: 詳細 → 論理 (状態図などの定義を参照)、論理 → 詳細 (節単位で参照)
  - 同じ対応関係を 2 箇所に持たない (図と表が同じ対応を表すなら片方に寄せる)
- 冒頭は位置づけだけを書く
  - 用語の定義はその語の初出の場所に置く
- 名前の付け方: ディレクトリ名はサーバーのコンポーネント名 (connection / dispatcher / parser …)、ファイル名は責務名 (`connection_handler.md`)、README の題は対象の名前 (「コネクションハンドラーの仕様」)
  - 層を表す造語 (「接続層」など) は使わない

## 書き方

- 用語は [glossary.md](./glossary.md) の「採用する語」に従い、新しい語を導入するときは glossary に追加する (2026-09-09 確定)
  - 理由: 本にしたときに用語の揺れが最も目立つため、辞書を正として揃える
- 論理名で書き、実装名は括弧で添える: 接続 (Client)、セッション (Session)、内部セッション (THD)
  - 実装の命名が論理名と衝突する場合 (X Plugin は接続 1 本を表すオブジェクトを Client と呼ぶ) は、その旨を注記する
- 構成要素は「何を持つか」ではなく「何に責任を持つか / 何を決めるか」「いくつ存在し、いつ生まれていつ消えるか」「他の要素とどう関係するか」で説明する
- 造語を避ける
  - 「コアサーバー」「接続層」のような語を作らず、文脈ごとの平易な言い方 (「サーバー全体の `max_connections`」「内部セッション」) にする
- 因果で書く
  - classic protocol との違いは「制約 → 解消 → 効果」、性質は「前提 → 帰結」の形にする
  - 前提の置き場がない「帰結」を作らない
- 物理名の扱い
  - 図のノードや本文は論理名で書き、ソケット API に対応する段階だけ括弧で物理名を添える (socket / bind / listen、accept、recv / send、close)
  - プロトコルのメッセージ名 (`ServerHello`、`AuthenticateStart` など) は日本語に言い換えず、そのまま使う (「挨拶の通知」のような訳は不自然になる)
- 根拠の付け方
  - 詳細仕様 (reference) では、主張ごとにソースへの permalink (コミット固定 + 行範囲) を付ける
  - 行番号はローカルのソースで確認したものだけを書く
  - 「参照:」は入れ子の bullet にし、1 リンク 1 行で書く
  - 検証していないことは「未検証」と明示する (ビルド時定義の既定値、スレッド数の断定など)
- 箇条書きの規則
  - bullet 内で「。」を使わず、続きの文は入れ子の bullet に分ける
  - 全角と半角の間にスペースを入れ、括弧は半角にする
  - MUST / SHOULD は文末表現 (〜なければならない / 〜べきである) で表し、ラベルと文末を混在させない
- 翻訳 (WL の要件など) は原文に忠実にし、要件の追加も削除もしない
  - 原文の古い名称 (getCapabilities) には現行名 (`CapabilitiesGet`) を注記する

## 図

- 1 つのモデルを複数の見方で描き、役割を重複させない
  - sequenceDiagram は「誰と誰がやり取りするか」
  - flowchart は「段階と分岐」
  - stateDiagram は「状態と遷移」
- 参加者名は誤認を避ける
  - プロトコルの図 (protocol/) では、プロトコルの端点として「クライアント」「サーバー」と書く
  - X Plugin 内部の要素「接続 (Client)」が同じ図に登場する場合 (connection/) は、接続元を「クライアントプログラム」と書いて区別する
- 図の中の境界: box で「クライアント側 / サーバー側 › X Plugin / サーバー側 › X Plugin の外」を分け、X Plugin が mysqld と同じプロセス内にあることを Note で示す (mermaid の box は入れ子にできない)
- 概念モデル (`docs/model/`) の語彙 (接続、セッション) と仕様書の論理名を一致させる

## 用語

- X Protocol: 通信規約
  - フレーム + protobuf メッセージの規約そのもので、`.proto` ファイルが仕様の正
- X Plugin: サーバー側の実装
  - X Protocol を待ち受け、接続処理・capability・認証・Notice・SQL 実行・ドキュメントモデルを担う
  - mysqld と同じプロセスで動く
- X DevAPI: クライアント側の API 仕様
  - MySQL Shell や各言語の Connector が実装し、内部で X Protocol を話す
- コネクションハンドラー: X Plugin のうち、接続の受付からセッションの確立・切断までを担う部分
  - minesql では X Plugin 型のハンドラーを 1 つ作ればよく、classic 用のハンドラーに相当するものは不要
- 内部セッション: 利用者の身元と実行状態を持ち、その利用者として SQL を実行する SQL 層側の場
  - 実装上は THD で、X Plugin のセッションと 1 対 1 に対応する
